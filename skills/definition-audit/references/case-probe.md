# 反例 Case 探测（可判定性 / 无歧义 / 正交性 / 完备性 / 边界清晰的子能力）

本文档是 `definition-audit` 的子能力，服务于「维度 1 可判定性 / 维度 2 无歧义 / 维度 3 正交性 / 维度 4 完备性 / 维度 5 边界清晰」的实操。审核这些维度不能只读措辞，还要造 case 让被审定义暴露问题。本文档提供造哪些 case、造多少个、如何记录反例、如何据此定位缺陷的方法。

术语沿用主 SKILL.md「术语约定」章节：**被审定义**、**定义单元**（类目 / 字段 / 判据条目 / 枚举值 / 状态之一）、**下游使用方**（代码 / 提示词 / 脚本 / 配置 / 其它 skill）。本文档不绑定任何具体项目或领域。

定位：主 SKILL.md 说明"要造代表性 case"；本文档说明"如何造、造什么、判据是什么"。仅当审核触及可判定性 / 无歧义 / 正交性 / 完备性 / 边界清晰任一维度时展开本文档；不影响 case 归位的纯措辞问题不在此处理。

## 何时展开本子能力

审核过程中出现以下任一情况时，进入本流程：

- 需要判断"读者能否稳定归位任意 case"（可判定性）。
- 需要判断"两个定义单元是否重叠 / 是否有 case 落不下去"（正交性 / 完备性）。
- 需要判断"某定义单元的边界是否只覆盖它自己"（边界清晰）。
- 需要判断同义或近义表述是否导致不同归位（无歧义）。
- 措辞看上去合理但没跑过 case，无法给出"是否可判定"的结论。

## 核心原则

- **case 优先于措辞**：先造 case、再看措辞；不造 case 得出的"可判定 / 不可判定"结论无效。
- **代表性 + 极端性并重**：既覆盖典型 case，也刻意造边界 case、跨类 case、缺信息 case。
- **数量按定义规模定**：小定义（≤ 3 个定义单元）不少于 6 个 case；中等（4~10 个定义单元）不少于 10 个；复杂（> 10 个定义单元 / 多层嵌套）不少于 20 个。
- **反例即证据**：任何"这里判不准 / 会重叠 / 会落空"的结论必须绑定具体 case，禁止凭感觉。
- **一 case 一结果**：结果遵循被审契约，可以是单一归属、标签集合或复合字段；同一 case 由多个读者独立判断，约定结果不一致说明可判定性闸口失败，再按主 SKILL.md 的归位顺序定位根因。
- **类型是测试策略，不是缺陷分类**：六类 case 可以重叠。记录一个主类型，并用标签补充其它测试策略，不要求六类互斥。
- **先判适用性**：逐类记录适用、结构性不适用或未覆盖。例如只有一个定义单元且不存在竞争承载位置时，跨类策略可记不适用并说明依据；只是暂未想到 case 应记未覆盖，不能借此豁免或证明无缺陷。规模要求仍用其它适用策略补足，不虚构定义单元凑齐类型。

## Case 分类与造法

按下列六类分别设计 case，覆盖不同维度：

### 1. 典型 case（代表性）

- 目的：验证"最应该被稳定归位的输入"是否稳定归位。
- 造法：从每个定义单元的定义里挑最典型的一到两个特征，组装成 case。
- 判定：稳定归到该定义单元 = 通过；否则该定义单元存在可判定性缺陷。

### 2. 边界 case（边界清晰）

- 目的：验证定义单元的边界是否精确划清。
- 造法：故意让特征"贴着边界"——恰好满足最小成立条件、恰好不满足、临界值、临界范围。
- 判定：边界处判定与定义写的边界一致 = 通过；判定漂移 = 边界模糊。

### 3. 跨类 case（正交性）

- 目的：验证"是否存在合理 case 能同时落到两个定义单元"。
- 造法：把定义单元 A 的典型特征与定义单元 B 的典型特征组合到同一 case。
- 判定：对已覆盖输入能稳定确定约定归属或集合 = 通过；本应单选却多归属、集合成员不确定或字段争夺同一职责 = 正交性缺陷；无处可归 = 完备性缺陷。明确允许同时命中的多标签不因此失败。

### 4. 落空 case（穷尽 / 完备性）

- 目的：验证"是否存在合理输入落不到任何定义单元"。
- 造法：从已知输入空间中挑"看起来该被覆盖但被审定义没提"的场景；或从下游使用方实际会出现的极端场景倒推。
- 判定：能落到某单元或明确落到"兜底单元 / 显式声明不覆盖" = 通过；无处可归 = 完备性缺口。

### 5. 缺信息 case（失败路径 / 完备性）

- 目的：验证"当输入不满足前提时被审定义如何指导判断"。
- 造法：故意缺少判据依赖的关键信息、上下文、字段值。
- 判定：被审定义有明确"信息不足时怎么处理"的分支 = 通过；无处理路径 = 失败路径缺失。

### 6. 语义近邻 case（无歧义 / 边界清晰）

- 目的：验证相邻概念是否被稳定区分。
- 造法：把两个易混淆概念的特征各取一半构造，或把同一 case 用两种同义术语描述再对比。
- 判定：判定结果一致 = 通过；仅因表述变化导致结果不同 = 无歧义缺陷；因单元适用范围不清导致结果不同 = 边界清晰缺陷。

## 反例记录模板

每个触发问题的 case 必须记录以下字段，作为审核结论的证据：

```markdown
- Case ID：<C-01>
- 主类型：<典型 / 边界 / 跨类 / 落空 / 缺信息 / 语义近邻>
- 标签：<可选；其它同时命中的测试策略>
- 描述：<用一到两句话完整描述该 case 的输入特征>
- 期望归属：<按被审定义应得到的单元、标签集合或字段结果；如无法确定则写"应有但无">
- 实际能否稳定归位：<能 / 不能 / 非预期多重归属 / 无处可归>
- 独立判断：<审核者 A 结果；审核者 B 结果；无第二审核者时写"未独立复核">
- 可判定性结果：<通过 / 失败>
- 主维度：<无歧义 / 正交性 / 完备性 / 边界清晰 / 其它维度 / 框架外>
- 次生影响：<可选；不得作为第二条主问题重复计数>
- 定位到的定义位置：<文件#行>
- 下游影响：<下游使用方会因此产生什么误判 / 报错 / 降级>
- 证据置信度：<已独立复核 / 单评估者>
```

## Case 池规模指引

| 定义规模 | 最少 case 数 | 覆盖要求 |
| --- | --- | --- |
| 小（≤ 3 个定义单元） | 6 | 各适用策略至少覆盖 1 次，剩余补典型/边界 |
| 中（4~10 个定义单元） | 10 | 各适用策略覆盖 1~2 次，跨类 case 覆盖主要邻接对 |
| 大（> 10 个定义单元 / 多层嵌套） | 20 | 各适用策略均覆盖，跨类 case 至少覆盖每一对高相似定义单元 |

跨类 case 的邻接对选择：先扫被审定义找"名字近 / 语义近 / 判据近"的成对定义单元，逐对造跨类 case。

## 判定标准（本子能力出口条件）

进入下一步前必须满足：

- 已造出并记录不少于按规模指引要求的 case 数，且每个被审定义单元均有已评估的典型 case；数量达标不能替代覆盖。
- 六种策略均已检查适用性，各适用策略至少覆盖一个；不适用项有结构依据，未覆盖项作为验证缺口而非通过。允许一个 case 通过主类型和标签覆盖多种策略。
- 触发的问题都已按反例记录模板记录，并绑定到主维度或框架外标记及定义位置。
- 稳定归位率、跨类无重叠率、无落空率给出已评估样例的分子、分母和结论；分母为零时记录不适用或未覆盖，不输出 100% 通过。不把样例通过率外推为全部真实输入的通过率。
- 无第二位独立审核者时，所有可复现性结论标记为"单评估者"，不得声称已完成独立复核。

## 常见误区

- **只造典型 case**：得出"看上去可判定"的乐观结论，遗漏边界与跨类问题。
- **case 描述太笼统**：无法复现，读者不同判定结果无法归因是被审定义问题还是 case 问题。
- **一次判就下结论**：单人单次判断不足以验证可判定性，至少要能被"另一位读者按同一被审定义独立判定"复现一致。
- **造完不记录**：不写下反例就等于没造；下次审核无法回溯。
- **case 与真实场景脱节**：造出实际不会发生的 case，虽能触发被审定义缺陷但不代表真实风险，需在记录中标注真实性。

## 禁止事项

- 禁止在未造 case 的情况下给出"可判定 / 不可判定"结论。
- 禁止仅用典型 case 覆盖审核，跳过其它策略的适用性判断；不适用必须有结构依据，不得用缺少样例替代。
- 禁止把"case 造不出来"当作"被审定义没问题"；只能记录已尝试的邻接对与未发现反例的范围，不能据此证明单元互斥，仍需完成落空 case 与缺信息 case 的探测。
- 禁止在反例记录中省略"下游影响"——没有影响判断的问题不构成有效审核证据。
