# 问题定义（“定义核心问题”的子能力）

本文档是 `problem-solution-design` 的子能力，服务于“定义核心问题”。当初步分析后仍无法去除方案预设、区分多个问题或形成可判定目标时，按本文档把用户表述收敛为一个定义清楚、可被解决、可被验证的核心问题。

定位：主流程负责完整的问题定义，包括问题类型和主要取舍；本文档只深入去假设、因果追问与根因定位、方案倒推、成功判据、约束分层、边界划定与问题成立性验证。事实核验可以穿插进行，但核心目标和不可变约束未稳定前不得最终选择方案；流程控制以主 `SKILL.md` 的元规则为准。

## 何时展开本子能力

第 1 步剖析时出现以下任一情况，进入本流程：

- 用户给的是“现象”或“情绪”（“太慢了”“很难用”“老是出问题”），没有可度量的目标。
- 用户直接给的是“方案 / 动作”（“加个缓存”“换成消息队列”“加个开关”），而没有说清要解决的问题。
- 目标写不出成功判据，只能用“更好 / 更稳 / 更快”这类不可验证的词描述。
- 一个诉求里裹了多个问题，范围不清、主次不分。
- 问题反复出现，或此前已按某个原因修过却复发——提示真正的根因还没被定位。
- 不确定这是不是“真问题”——没人能说清不做会怎样、影响谁、发生频率。

## 核心原则

- **问题先于方案**：先定义清楚要解决什么，再谈怎么解决；用户给方案时先倒推它要解决的真问题。
- **可验证优先**：核心目标必须带成功判据（数值、行为、范围），不可证伪的目标不算定义完成。
- **一次一个核心问题**：一个诉求里若裹了多个问题，先拆分并确定本次主问题，其余登记为后续项，不在一个方案里混解。
- **区分症状与因果假设**：先定义现象暴露出的目标差距或待改变状态，再用证据验证原因；需要先止血时，显式声明“本次只缓解症状，不声称消除根因”。
- **追因到可控根本**：问题复发或表层修复失效时，沿证据从直接原因逐层追到能被本次改动消除的根本原因，而不是围着最先想到的表层原因反复打补丁；证据追不到根因时如实标注深度，不用猜测填补。
- **去假设**：重述问题时不夹带解法、不夹带原因猜测；假设必须显式标注为“待验证前提”，不能当既定事实。
- **范围收敛**：定义阶段主动划掉“不在本次解决”的部分，防止问题在后续膨胀。

## 方法

默认按以下顺序展开，每一项给出可判定的产出；现象、触发条件、影响范围和因果假设需要证据时，可以与事实核验穿插，不要求先完成未经验证的“根因定义”。

### 1. 复述并去假设

用一句话复述用户的原始诉求，只保留“谁 + 在什么场景 + 遇到什么 / 想要什么”，剥掉其中夹带的解法与原因猜测。

- 剥离解法：把“加缓存 / 加索引 / 加开关”这类动作从问题描述里摘出，另记为“候选解法”，不写进问题本身。
- 剥离归因：把“因为 X 所以慢”这类未验证的因果摘出，标为“待验证前提”。
- 回读校验：抽取原话的`主体 + 核心动作/属性 + 对象`，逐项映射回复述，确认没有把核心动作换成相邻的另一个动作（例：“及时停止”被换成“判断闭合”，“能不能”被换成“快不快”）。仅关键词重叠（如都含“时/when”）不算映射成立；引入原话没有的动词或对象却给不出依据，即为理解偏移，回到原话重述。当术语替换可能改变问题类型（控制↔判据、能力↔性能、正确性↔效率）时，回显一行“我理解要解决的是 X（原话核心动作=…）”供用户快速纠偏。
- 产出：一句不含解法、不含未验证归因、且核心动作能回读对齐原话的问题复述。

### 2. 分离现象、触发条件与待改变状态

把“看得见的现象”与“真正想要的结果”分开，形成可验证的因果假设。

- **现象**：用户能直接观察到的表现（报错、卡顿、数据不对、操作绕）。
- **触发条件**：在什么输入 / 环境 / 时机下出现，是否可稳定复现，覆盖多大比例场景。
- **待改变状态**：现象暴露出的目标差距，或本次需要改变的可观察状态。连续追问“这为什么是个问题 / 它导致了什么”，直到得到可验证、可被本次影响的状态；继续追问会超出本次范围或触及不可变约束时停止。
- **因果假设**：对“什么导致现象”只形成待验证解释，写明支持证据和反证条件；不得在取证前把猜测命名为根因。
- **根因追溯（问题复发或表层修复失效时展开）**：沿证据把因果链写成`现象 -> 直接原因 -> 中间原因 -> 根本原因`，每层标注 `事实 / 推断 / [未验证]`。停止条件三选一：追到能被本次改动消除、且消除后现象不再复发的可控原因；追到不可控外因（记为约束，不继续外扩）；证据耗尽（如实标注当前追到的深度，转最小验证或显式声明只做症状缓解）。不因“最先想到的原因能解释现象”就停在表层。
- **因果链校验**：对拟定的根本原因做反向验证——“移除它，现象是否不再发生”；只有相关性、无消除性证据的原因标为 `[未验证]`，不得当作根因写入定义。
- 追问要收敛而非发散：每一层都指向“可被本次改动影响的对象”，追到不可控外因即停，并把该外因记为约束。
- 追问不得改变主体与核心动作：若某层 why 的答案引入了新的动作或对象（如“及时停止”滑向“判断闭合”），这是分叉到另一个问题，应登记为独立/下层问题，并显式决定是否切换主问题，而不是就地替换原问题。
- 产出：`现象 -> 触发条件 -> 待改变状态`，以及必要的因果假设和验证动作；触发根因追溯时附`现象 -> … -> 根本原因`因果链及每层证据等级。

### 3. 用户给方案时，倒推真问题

当用户给的是方案 / 动作而非问题时，先还原它要解决的问题，再判断该方案是否对症（对症判断留给第 4 步八问的问 1，这里只负责“还原问题”）。

- 追问“这个方案是为了达成什么”：把方案换成它承诺的结果。例：“加缓存” -> “想让某接口在某负载下的 P99 从 A 降到 B”。
- 追问“不用这个方案，问题还在不在”：若换个做法问题同样能解，说明真问题在结果层而非该方案本身。
- 产出：方案背后的真问题陈述 +（可选）该方案作为“候选解法之一”登记，等待第 3 步与其他候选一起比较。

### 4. 定义可验证的核心目标

用一句可验证的语句描述“本次要达成的状态”，必须包含成功判据。

- 判据三选一或组合：**数值**（指标从 A 到 B、错误率 < X）、**行为**（某操作在某条件下产生某结果）、**范围**（覆盖哪些场景 / 用户 / 链路）。
- 判据必须可在落地后验证：给出验证手段（指标、用例、走查）；给不出验证手段的目标视为未定义完成。
- 判据必须反向对齐原始诉求：自问“如果这个判据达成，用户原话的诉求是否真的被满足”。例：判据“能准确判断任务闭合”达成时，“work agent 及时停止”仍可能不满足（判得准仍可能停不下来），说明判据服务的是错误问题，回到复述重定义。
- 目标要“够窄”：判据共同服务于同一目标；只有彼此独立、会导向不同方案的判据才拆成多个问题。
- 精确数值暂缺但不影响排除或验证候选时，不把补齐数值作为前置阻塞；可先使用行为、范围或相对变化判据。
- 产出：一句“核心目标 + 成功判据 + 验证手段”。

### 5. 约束分层

列出会限制方案空间的约束，分三层，避免定义阶段就把不可变约束当成可选项。

- **项目约束**：技术栈、目录结构、既有约定、术语（以仓库 AGENTS.md 与相邻模块为准）。
- **资源约束**：时间、人力、可用数据、可用环境。
- **不可变约束**：线上行为、对外接口、协议、鉴权与隔离边界、合规要求——这些是方案不能碰的红线。
- 产出：三层约束清单；其中不可变约束需显式标注“不可触碰”。

### 6. 划清边界

明确本次“解决 / 不解决”的范围，把超出范围的问题登记为后续项。

- 写出“本次解决 X”和“本次刻意不解决 Y（原因 + 登记为后续项）”。
- 边界要能挡住范围蔓延：任何“顺手也一起改了吧”的诉求，若不服务于核心目标，一律推到后续项。
- 产出：`解决 X / 不解决 Y（Y 登记为后续项）`。

### 7. 验证问题成立性

在进入方案前，确认这是一个值得解的真问题，避免为“不够优雅”或“可能出现”的假想问题设计。

- **谁受影响**：具体的用户 / 链路 / 场景，而非“大家可能都”。
- **发生频率与规模**：稳定复现还是偶发，覆盖多大比例。
- **不做的代价**：不解决会阻塞什么、引入什么风险、损失多少；若代价只是“看起来不够好”，标记为“暂不必要”并进入否决出口。
- **是否已有兜底**：现有配置 / 文档 / 流程是否已经能绕过或缓解。
- 产出：`真问题 / 暂不必要 / 待确认` + 依据。判为“暂不必要”时进入否决出口并给出重新评估条件；判为“待确认”时，根据缺失信息的归属进入主流程的澄清或验证出口。

## 常见定义陷阱（反例）

定义阶段最常见的失败模式，逐条自查是否踩中：

- **把方案当问题**：直接把“加缓存”写成核心目标，跳过了“要解决什么”。
- **偷换问题**：复述或追问时把用户的核心动作/属性替换成相邻但不同的问题（及时停止→如何判断完成、能不能→快不快、正确→高效），使成功判据服务于错误问题。自查：复述的动词与对象能否逐一映射回原话，而非仅关键词重叠。
- **把现象当待改变状态**：停在“接口慢”，没说明影响什么、在何种条件出现、改变到什么程度才有价值。
- **目标不可证伪**：核心目标用“更快 / 更稳 / 更好用”描述，落地后无法判断是否达成。
- **一锅烩**：一个目标里塞进多个问题，导致方案面面俱到、无一做透。
- **范围蔓延**：定义时不划边界，把“顺手优化”“未来可能要”都算进本次。
- **暂不必要**：为“可能出现的问题”或“看起来不够优雅的现状”设计，说不清谁受影响、不做会怎样。
- **停在表层原因**：抓住最先想到、能解释现象的原因就动手，问题修完复发；未沿证据把因果链追到可被本次消除的根本原因。自查：拟定原因移除后现象是否真的不再发生。
- **未验证前提当事实**：把“因为 X 所以慢”这类未验证归因写进问题定义，导致后续方案建在错误因果上。

## 判定标准（子能力完成条件）

问题定义完成的标志是能明确回答以下全部，缺一不可回到对应方法项补齐：

- 真正要解决的是什么（去解法、去未验证归因的一句问题陈述）。
- 做到什么程度算成功（可验证的核心目标 + 成功判据 + 验证手段）。
- 受什么约束（三层约束，含不可触碰的红线）。
- 什么不在本次范围内（明确的不解决项，已登记后续项）。
- （问题复发或表层修复失效时）根本原因是否已沿证据追到可控层级并经“移除即消除”校验，或已如实标注证据深度并声明只做症状缓解。
- 这是不是一个值得解的真问题（真问题 / 暂不必要 / 待确认 + 依据）。

## 推荐输出格式

```markdown
- 原始诉求复述：<去解法、去未验证归因的一句话>
- 回读校验：原话核心动作/对象 = <...>；复述核心动作/对象 = <...>；<一致 / 术语替换（依据）/ 已回显确认>
- 现象 -> 待改变状态：<现象> / <触发条件与复现范围> -> <落在可改动对象上的目标状态>
- 因果链（问题复发或表层修复失效时）：<现象 -> 直接原因 -> … -> 根本原因>，每层<事实 / 推断 / [未验证]>；停止原因<可控根因 / 不可控外因 / 证据耗尽>
- 方案倒推（若用户给的是方案）：<方案> -> <它承诺的结果 / 真问题>
- 核心目标：<可验证目标 + 成功判据（数值/行为/范围）+ 验证手段>
- 约束分层：项目<...> / 资源<...> / 不可变（红线）<...>
- 本次范围：解决 <X>；不解决 <Y>（原因 + 登记为后续项）
- 待验证前提：<被剥离出来、需在方案阶段验证的假设>
- 问题成立性：<真问题 / 暂不必要 / 待确认> —— 谁受影响 / 频率规模 / 不做的代价 / 是否已有兜底
```

## 验证清单

最终选择方案前必须自查；允许先进入主流程第 2 步收集证据。缺失可调查证据时转最小验证，不以尚未验证的根因阻止取证：

- 问题复述不含解法、不含未验证归因；被剥离的解法与假设已分别登记为“候选解法 / 待验证前提”。
- 复述的核心动作/属性能逐项回读对齐用户原话，未把问题偷换成相邻问题；无依据的术语替换已修正，改变问题类型的替换已回显确认。
- `现象 -> 触发条件 -> 待改变状态`完整；因果解释有证据或已标为待验证假设。
- 若问题复发或表层修复曾失效：因果链已追到可控根因（并通过“移除即消除”反向校验），或已如实标注追到的深度并转最小验证 / 声明只做症状缓解；未停在最先想到的表层原因。
- 核心目标带可验证的成功判据与验证手段，没有用“更快 / 更好 / 更稳”这类不可证伪的词。
- 一次只锁定一个核心问题；裹入的其它问题已拆出并登记后续项。
- 约束分三层且不可变红线已显式标注。
- 边界写清了“解决 X / 不解决 Y”，Y 已登记后续项。
- 问题成立性有结论与依据；暂不必要的问题未被推进，待确认的问题已按缺失归属进入澄清或验证出口。
- 已对照“常见定义陷阱”逐条自查，未踩中或已修正。

## 禁止事项

- 禁止把用户原话或用户给的方案直接当作核心问题，跳过复述与倒推。
- 禁止把用户的核心动作/属性偷换成相邻但不同的问题（如“及时停止”换成“判断闭合”），或让成功判据服务于偷换后的问题。
- 禁止把“现象 / 表层”直接当作待改变状态，或把未经证据支持的因果解释写成根因。
- 禁止在问题复发时停在最先想到的表层原因反复打补丁，而不沿证据追根因或如实标注证据不足。
- 禁止把未验证的因果归因写进问题定义并当作既定事实。
- 禁止用不可验证的目标（更快 / 更稳 / 更好用）作为核心目标。
- 禁止在一个核心目标里塞进多个问题而不拆分。
- 禁止在定义阶段不划边界，放任范围蔓延到“顺手改 / 未来可能要”。
- 禁止为暂不必要的问题擅自进入方案设计，或把可调查缺失全部退回给用户。
