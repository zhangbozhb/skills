# 问题定义：按卡点展开

主流程负责决策、证据、八问与输出。问题定义始终遵循主文档的[高级推理视角与整体原则](../SKILL.md#高级推理视角与整体原则)；本文的具体拆解方法按需展开，得到足以继续的结果即回到主流程。文字已清楚也要检查边界、前提与价值是否成立，不把“能复述”当成“定义正确”，也不把全部方法变成固定问卷。

## 选择调查方法

问题类型只用于选择调查动作，可以并存，不当作原因或方案结论：

| 暂定类型 | 优先调查什么 |
| --- | --- |
| 目标或价值冲突 | 不同角色的成功判据、成本承担和已确认排序；只能由用户决定的取舍再询问 |
| 系统或资源约束 | 当前上限、依赖契约、负载条件、限制是否可调整及调整代价 |
| 流程缺陷 | 角色、交接、等待、例外处理与责任边界；用实际记录定位阻塞 |
| 实现缺陷 | 入口、状态或数据流、复现、相邻实现与测试证据 |
| 认知或证据缺口 | 有分歧的前提、证据来源与适用条件，以及能区分解释的最小验证 |

例：审批慢可能来自等待，也可能来自材料反复补充。仅知道“总耗时长”还不能选择增加审批人或重写系统；先查看各阶段停留与返工记录。

**带回主流程**：本轮优先调查对象、它会改变哪项判断、预期能得到什么证据。

## 还原结果并校验语义

1. 从原话提取主体、核心动作或属性、对象及场景。用一句话表达希望改变的状态，剥离解法和未验证归因，分别记为候选与假设。
2. 用户直接给方案时，先从上下文推导它承诺什么结果；判断换一种做法是否也能实现同一结果。“考虑加缓存”是候选提议，“只能用现有缓存服务”才是明确约束。前者不自动限制候选空间，后者未经用户同意不能取消。
3. 用成功判据反向校验：判据达成时，原始诉求是否仍可能失败？若会失败，找出遗漏的行为或被偷换的目标。语义等价的表达可直接使用，不要求逐词一致。

例：“让工作 agent 在任务完成后及时停止”不能只变成“准确判断任务完成”；还需明确停止条件、停止动作和可观察时限。完成判定可作为子问题，不能代替停止行为的验收。

例：“加缓存”可能为了降低响应时延，也可能为了减少外部调用费用。应根据已有证据还原目标，不能把熟悉的缓存用途直接当成用户诉求。

有两种合理解释且会导向不同方案时，先检查现有材料；仍只能由用户决定或提供的信息，才简明回显差异并按主流程询问。这里的追问优先用于分析，不要求逐条向用户提问。

**带回主流程**：去解法与未验证归因的问题陈述；如有歧义，列出具体分歧及其影响。

## 确定成功状态与边界

先分离容易混在一起的内容：

| 内容 | 要回答的问题 |
| --- | --- |
| 现象 | 用户或系统实际观察到什么？ |
| 触发条件 | 在什么输入、环境、规模与时机下出现，频率与影响范围如何？ |
| 待改变状态 | 该现象妨碍哪个结果，本次要把状态改变到什么程度？ |
| 因果假设 | 什么机制可能导致现象，支持与反证是什么？不得先当成事实 |

沿“为什么这构成问题、它影响什么”追到可验证且与本次诉求相关的结果。判断所需的上游原因、下游后果与利益影响应纳入分析；继续追问已不能改变本轮判断时停止，不因超出模块或实施范围就提前忽略。若引入新的目标或对象，标明它与原问题的依赖关系，不把更宏观的目标自动替换为本轮目标。

- 将“更好 / 更快 / 更稳定”落成可检查的状态：指标阈值、输入条件下的行为，或需要覆盖的范围，并说明如何观察。只写“指标改善”但无足以区分候选的判据仍不够。
- 指标必须服务于用户结果。吞吐增加却导致错误结果更多，不能仅因吞吐达标认定成功；把必须保持的正确性等要求写入底线。
- 同一结果可以包含多个判据。若它们存在依赖或需要共同权衡，保留在同一方案；可独立决定且互不影响的问题再拆分。
- 优先处理最限制目标的事项，保留必要依赖。范围外内容只说明排除理由；只有明确承诺后续或接受暂时缓解时，才记录相应行动或债务。
- 数值缺失但行为或范围判据已足以选型时继续；不同阈值会反转选择且只能由用户决定时，走澄清。

例：“每日批量导入按时完成且数据正确”允许同时包含完成时限、数据一致性和异常处理要求。不能为“一次一个问题”把数据正确性排除在性能方案验收之外。

**带回主流程**：`目标状态 + 成功判据 + 验证方式 + 必须保持的底线 + 本次范围`。

## 检视定义背后的边界与价值

用整体原则复核问题定义是否站得住；深入程度取决于相关影响，不要求每次单独输出这张表：

| 视角 | 定义阶段的检查 | 如何落到定义中 |
| --- | --- | --- |
| 目标与因果 | 指标对应真实结果吗？原因是证据支持的机制，还是附在现象上的猜测？ | 保留原诉求，分开目标差距、因果假设与候选做法；有疑问则写验证条件 |
| 系统边界 | 谁在上游产生输入、谁在下游承接结果，哪些依赖决定目标能否成立？ | 补足分析范围和接口条件，说明本次实施能改变什么、哪些外部因素仍需观察 |
| 演化与反馈 | 方案实施后，负载、阶段或参与者行为会怎样改变？当前指标可能掩盖什么延迟后果？ | 给出时间窗、阶段前提、观察信号和重判条件，避免将静态结果外推为长期结果 |
| 价值、激励与权力 | 谁定义成功、受益或承担成本？考核会鼓励什么行为，受影响者能否提出异议或纠正？ | 明确价值排序、不可转移的代价和责任边界；需要用户决定的取舍单独提出 |

例：用户希望客户问题更快解决，团队提出提高工单关闭率。若提前关单会导致用户反复提交，关闭率达标并不表示目标达成。定义应检视实际解决时长、重复提交等证据，以及关单考核是否诱导偏离目标；即使本次只能调整一个团队的流程，也要评估跨团队转交与用户负担。指标阈值和价值取舍不能由模型自行编造。

如果这些检查支持原有边界、目标和判据，可以明确保留；发现遗漏则修正，涉及用户目标、价值排序或实施范围变化时按主流程处理。**带回主流程**：定义为何成立或需要修正、支持依据、适用条件和仍需决定的事项。

## 定位当前关键

沿以下关系查找当前投入点，执行规则遵循主流程的[聚焦当前关键与动态校准](../SKILL.md#聚焦当前关键与动态校准)：

1. **已成立的能力**：已有证据支持什么，覆盖哪些输入、规模和环境，现在是否仍适用？
2. **剩余的目标差距**：哪些未满足判据最影响结果？局部耗时、错误率等指标可以提示候选瓶颈，仍需解释改变该环节如何影响整体结果；有直接测量或验证支持后再将其作为当前关键。
3. **可干预的环节**：改善、绕开或消除它会如何推进整体结果，支持这种判断的证据是什么？局部做到极致仍不影响目标时降低优先级。
4. **重判条件**：什么新证据、规模变化或瓶颈解除会改变以上判断？只更新受影响部分，目标与价值取舍变化按主流程处理。

例：100 万条导入已在目标规模验证正确，但耗时超标，测量显示主要时间花在匹配扫描。当前关键可以转为匹配效率，正确性继续作为验收底线；只有少量样本跑通时不能直接作此判断。若性能改善后人工审批成为主要延迟，应重排后续投入。

**带回主流程**：`当前场景与已验证能力 → 当前关键及依据 → 优先投入 → 重判条件`。依据不足时，把需要验证的影响关系作为关键未知。

## 追查因果机制

将可观察现象、触发条件、影响和解释分开；问题复发或方案依赖某个解释时，按主流程的[因果追查与停止条件](../SKILL.md#因果追查与停止条件)展开：

- 写出从触发到结果的主要机制，每条连接标记事实、推断或待验证。复杂问题可以有多个共同原因，不强制单线因果链。
- 优先检查此前修复为何失效：遗漏了哪些条件、只是压住了症状，还是环境已改变？
- 对候选原因寻找反证或干预证据：改变该因素后，同等条件下结果是否消失、减轻或仍然出现？比较替代解释，不能只找支持最初判断的材料。症状减轻只支持干预有效的有限结论，还需机制证据判断是否解决根因或仅作缓解。
- 追到可干预机制且证据足以选择方案时收敛。外因不可控不代表本次无解，继续检查隔离、背压、重试限制或流程边界能否切断影响。
- 原因仍不清且会决定方案时，返回最小验证。需先止血时说明缓解范围，并使用主流程的[显式缓解](../SKILL.md#显式缓解)规则，不承诺根因已消除。

例：请求超时后反复扩容仍复发，不能只归因为“容量不足”。检查慢依赖、无界重试和队列积压是否形成放大循环；可以用受控复现、重试计数和队列指标支持或推翻机制。上游暂时不可改时，限制重试也可能切断放大，但要验证失败处理与用户影响。

**带回主流程**：机制及证据、尚未排除的解释、可干预位置、停止追查的理由或下一验证。不得把设计后的验收结果写成已经取得的因果证据。

## 分离约束与假设

不要把“项目、资源、安全”等约束来源与“不可变”混成互斥类别。分别记录：

| 维度 | 内容 |
| --- | --- |
| 来源与依据 | 用户明确要求、适用规范、接口依赖、实测资源上限或现行惯例；给出可追溯出处 |
| 适用范围 | 在什么场景、规模、时间窗和对象上成立 |
| 可变性 | 本次必须保持，或允许调整但需迁移、资源及有权者决定；不能确定时写明缺失 |
| 证据状态 | 已确认事实、推断或待验证；待验证不代表允许改变，已确认也不等于永久不变 |

对影响候选的“必须 / 不可能”应用主流程[关键前提检验](../SKILL.md#关键前提检验第一性原理)，追问目标所必需的条件以及现有做法是否唯一：

- “必须按序展示”约束可观察结果，不自动证明全部计算必须串行。并行计算后按序提交可作为候选，再验证共享状态、失败处理、缓冲上限与总成本。
- “当前资源下理论下界已超过目标”需要核对下界模型和资源约束；假设均有依据时，可以得出该条件下不可行，不必为了创新反复质疑。
- 用户明确要求数据不离开设备时，外部服务不能因性能更好成为合规候选；质疑惯例不等于忽略有效约束。

**带回主流程**：关键约束与出处、被拆出的假设、反例或替代方向、最小验证。只有会改变选择的前提需要展开。

## 判断问题成立性

检查受影响对象、发生频率或可信风险、规模、不做代价、机会收益及已有兜底。成本收益可定性，不为看似精确编造数值。

- **值得推进**：目标差距或预期损失有证据，解决后有实际价值。预防问题不必等待事故发生，但须说明发生机制与影响依据。
- **暂不必要**：已有能力足够、代价小于改动成本，或只有审美偏好却无目标收益；给出不做依据与重新评估条件。
- **证据不足**：指出哪项未知会影响判断；可调查的给最小动作，只能由用户决定的给最少问题。

**带回主流程**：判断与依据。是否值得解决和某个候选是否可行是两个判断，不因一个方案失败就否定问题本身。

## 完成条件与带回信息

用以下信息检查是否足以继续，不要求另交一份重复报告：

- 问题陈述与原诉求语义一致，预设方案和未验证归因已分开。
- 目标有成功判据与验证方式；主次、必要依赖、底线和本次范围清楚。
- 分析范围覆盖影响判断的依赖、相关角色和时间条件，已区分指标达标与真实目标达成；必要的边界或价值取舍已明确。
- 当前关键有适用场景与证据；尚未确定时，已指出哪条影响关系需要验证。
- 决定方案的约束和因果前提有依据，或明确标为待验证；缺口的归属与下一动作清楚。
- 是否值得解决有当前判断；继续调查、询问或进入选型的理由明确。

带回主流程的信息可合并为：`问题与目标 → 当前关键及依据 → 约束、取舍与范围 → 关键前提状态 → 下一步`。缺少决定性证据不妨碍先进入取证，但不能把“已形成问题定义”写成“方案已可推荐”。
