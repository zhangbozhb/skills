# 问题与方案设计

本 skill 将“想做某件事”收敛为“为什么做、做到什么算成功、具体怎么解决”。核心产出是与项目现状一致、可实施、可验证、可回退的推荐方案，而不只是问题分析或是否值得做的判断。只有缺少用户决策、证据不足或确认不应实施时，才降级为澄清、验证或否决输出。

## 使用边界

使用本 skill：

- 用户描述了现象、模糊需求或未经验证的方案。
- 同一问题存在多个候选，需要比较取舍。
- 用户质疑方案是否对症、必要、过度、值得投入或存在安全风险。
- 设计会改变接口、流程、数据边界或多个模块，需要先审查再实施。

不使用本 skill：

- 目标和实现范围已明确，用户要求直接写代码、修复明确 bug 或运行命令。
- 纯信息查询、文档检索、状态汇报。
- 已确认方案后的实施步骤，且没有新的设计取舍。
- 审核已经写好的 schema、分类体系或字段协议本身；这类结构性定义审核使用定义审核类专项能力。

## 输入与出口

输入至少包含用户当前诉求；项目文件、运行数据、约束和历史决策按需获取。

本 skill 的默认产物是方案或其它合法出口，不自动授权实施。用户只要求分析、评估或设计时，不修改正式实现；安全可逆验证也需说明写入范围，涉及副作用时先检查授权。

请求适用本 skill 后，优先收敛到解决方案出口；不适用时直接返回原任务，不算流程出口：

- **澄清出口**：缺少只能由用户提供、且会改变目标、价值排序、范围或授权的信息，默认提出不超过 3 个归并问题后停止；无法归并的独立安全或不可逆取舍可分轮询问。
- **验证出口**：不确定性可通过代码、数据、调研或安全可逆实验消除，但当前证据不足以选定方案；给出当前候选方向、最小验证动作和选型门槛，不能只列调查项。
- **否决出口**：证据足以证明问题暂不必要或所有候选均不值得实施；给出否决依据和重新评估条件，不强制追加无价值的验证。
- **解决方案出口**：至少一个候选通过八问；输出推荐方案的工作机制、关键改动、实施步骤、验收与回退，并说明为何优于其它候选。

## 流程控制元规则

本 skill 约束的是决策质量、必要检查和合法出口，不规定唯一推理路径。模型应根据问题复杂度、风险、已有信息和工具能力选择最高效的执行方式；不得为了形式完整机械展开全部步骤，也不得以“自主判断”为由绕过必要约束。

### 决策不变量

无论采用何种推理路径，以下结果必须满足：

1. 先确认真实问题与成功判据，不把用户给出的动作直接当作目标，也不把问题替换为相邻问题；复述须可回读对齐用户原话。
2. 问题复发或表层修复失效时，把因果追到可控根因再动手，不在表层反复打补丁；证据够不到根因时如实标注或显式转为症状缓解。
3. 关键结论区分事实、推断与未验证项，证据强度匹配决策风险，不机械要求每条判断都有两份证据。
4. 新增加法前检查不做、删除、合并、复用、回滚或约定替代的可能性。
5. 证据不足时优先消除最大不确定性的最小动作，不一次性索取所有理想信息。
6. 候选必须先通过对症性；失败候选可以淘汰，不反复包装到通过。
7. 不为未发生、无证据的未来需求新增抽象、模块或字段。
8. 高副作用、不可逆取舍、权限或数据边界不明确时触发检查点；安全边界不能用 ROI 抵消。
9. 有候选通过八问时必须进入解决方案出口，不得只给判断或审查摘要；没有可推荐方案时才进入澄清、验证或否决出口。

### 自适应执行权限

在不违反决策不变量和步骤依赖的前提下，模型可以：

- 合并相邻步骤，穿插问题定义与证据收集，或并行调查彼此独立的证据。
- 根据已有证据跳过重复调查，但需说明复用了什么证据；不得把“模型已知”当作项目事实。
- 自主选择工具、检索范围和分析方法，不受示例中的文件或命令限制。
- 根据真实取舍决定候选数量；没有实质分歧时不为凑数生成候选。
- 动态分配八问深度：低风险且证据明确的维度可一句话判定，高风险、冲突或未验证维度必须展开。
- 当表层分析无法解释问题、候选趋同或局部最优可能损害整体时，按需启用“高级推理视角”重新审视问题边界和候选空间。
- 采用比默认路径更高效的推理方式，只要最终产物能映射回必要检查与合法出口。

以下不属于可自适应项：跳过问 1 的对症性闸口、降低安全与隔离标准、把未验证判断写成事实、在授权不明确时执行高副作用操作、强行推荐未通过审查的候选。

### 高级推理视角（按需启用）

高级视角只用于重构问题或扩展候选，不重复证据地图、最小验证和八问。仅在当前因果解释站不住、候选只是局部变体、阶段变化可能反转收益，或不同角色存在激励与权力冲突时，选择相关视角：

| 视角 | 检查问题 | 必须落到的产物 |
| --- | --- | --- |
| 边界与因果 | 问题对象、责任边界和因果链是否画对？什么证据会推翻当前解释？ | 修正后的问题边界、因果假设、反证条件或新候选 |
| 演化与反馈 | 规模、阶段或参与者响应变化后，局部收益是否会变成整体代价？ | 阶段边界、反馈风险、切换或停止条件 |
| 价值、激励与权力 | 谁受益、谁承担成本、谁能决定或拒绝？方案是否诱导反目标行为或转移风险？ | 价值排序、治理约束、授权、申诉、隔离或审计要求 |

使用约束：

- 高级视角必须改变问题定义、因果假设、候选、阶段边界或风险控制中的至少一项；否则停止展开，不输出抽象议论。
- 抽象判断不能替代项目证据、八问审查或用户对价值取舍的决定。
- 默认在内部完成，只输出影响决策的结论及依据；除非用户要求，不展示哲学术语或单独生成“高级分析”章节。
- 多个视角得出冲突结论时，将冲突转化为待验证前提或用户检查点，不凭抽象偏好裁决。

### 默认参考路径

以下第 0～5 步是信息不足或问题复杂时的默认路径，不是必须逐段展示的固定流水线。简单问题可以在一次分析中完成多步；复杂问题可以在发现新证据后回到前序判断。只有依赖关系不可颠倒：未定义核心目标不得最终选方案，未建立必要证据不得给确定性结论，未通过问 1 不得继续推荐。

### 第 0 步：路由与检查点

目标：确认需要设计，而不是把执行任务流程化。

1. 判断请求是否落在“使用边界”内；不适用时停止使用本 skill，直接处理原任务。
2. 区分缺失信息：
   - **用户持有的关键缺失**：价值排序、目标阈值、范围、授权或外部事实只能由用户确认，且不同答案会改变方向。
   - **可调查缺失**：能从当前代码、指标、文档或安全可逆实验获得。
   - **非关键缺失**：不影响当前比较，可标注假设并继续。
3. 用户持有的关键缺失触发检查点；可调查缺失进入第 2 步或验证出口，不把调查工作退回给用户。

先尝试从现有信息定义目标；只有仍无法区分问题、约束和成功状态时，才展开 [references/problem-definition.md](references/problem-definition.md)。完成该尝试后，出现以下任一情况才触发 **CHECKPOINT / STOP**，先询问用户并停止方案推荐：

- 核心目标或成功判据仍存在多个会导向不同方案的解释。
- 必须由用户决定价值排序、范围或不可逆取舍。
- 涉及生产写入、删除、部署、发消息、付费调用、敏感数据或权限边界，且授权不明确。

若缺失可由安全调查消除，优先直接调查；暂时无法执行时，输出最小验证动作而不是只列问题。只有需要用户输入时才暂停，并输出当前已知事实、为何必须由用户决定，以及默认最多 3 个归并问题。

### 第 1 步：定义核心问题

目标：形成一个可验证、值得解决且边界清晰的问题定义。

需要形成以下结果；默认按此顺序展开，也可与证据收集穿插完成：

1. **去方案复述**：用一句话描述谁在什么场景遇到什么问题，不夹带解法和未验证归因。
2. **回读校验**：抽取用户原话的`主体 + 核心动作/属性 + 对象`，逐项映射回复述。复述若引入原话没有的动词或对象（如把“停止”换成“判断”、“及时”换成“准确”、“能不能”换成“快不快”），必须显式标注为术语替换并给出依据；无依据即判定为理解偏移，回到原话重述。仅关键词重叠（如都含“时/when”）不算映射成立。当术语替换可能改变问题类型（控制↔判据、能力↔性能、正确性↔效率）时，回显一行“我理解要解决的是 X（原话核心动作=…）”供用户快速纠偏。
3. **现象与触发**：记录可观察现象、触发条件、频率和影响范围。问题反复出现或此前修复失效时，沿证据把因果链追到可被本次消除的根本原因（`移除即现象消失`），不停在最先想到的表层原因；证据追不到根因时标注深度或显式声明只做症状缓解。
4. **问题类型**：判断是目标冲突、系统约束、流程缺陷、实现缺陷、认知或证据缺口，允许多项并存；该分类只用于选择验证动作，不作为结论。
5. **主要取舍**：说明当前阶段最重要的对立目标、价值排序，以及条件变化时何时需要重排优先级。
6. **核心目标**：写成“目标状态 + 足以区分候选的成功判据 + 验证方式”，并反向自问“判据达成时用户原话诉求是否真被满足”，不满足则回到复述。精确数值暂缺但不影响排除或验证候选时，不以此阻塞分析。
7. **约束与边界**：列出项目约束、资源约束、不可触碰的接口/鉴权/隔离红线，以及本次明确不解决的事项。
8. **成立性**：根据受影响对象、频率规模、不做代价和既有兜底，判定 `真问题 / 暂不必要 / 待确认`。

当初步分析后仍无法去除方案预设、区分多个问题或形成可判定目标时，展开 [references/problem-definition.md](references/problem-definition.md)。判为“暂不必要”时走否决出口；判为“待确认”时根据缺失归属进入澄清或验证出口。

### 第 2 步：建立证据地图

目标：只收集会影响决策的证据，并区分事实、解释和未知。

优先读取：

- 当前仓库的 `AGENTS.md`、相关 README、入口、相邻实现、测试和配置。
- 用户明确提供的指标、复现步骤、运行输出和已确认决策。
- 能证明影响范围、当前行为或约束的直接材料。

每条关键判断标记为：

- `事实`：有路径、命令输出、指标、复现或用户确认支撑。
- `推断`：由事实推出，写明推理链和反证条件。
- `[未验证]`：当前无充分证据，只能作为猜想或待验证前提。

证据规则：

- 结论风险越高，证据要求越高。涉及生产、安全、跨模块契约或不可逆变更时至少交叉验证两处独立证据。
- 用户偏好和价值排序以用户明确回复为证据，不强求第二来源。
- 成本和收益允许给区间或定性等级，但必须说明估算依据，不伪装成精确事实。
- 不证明“绝对不存在”；说明已检查范围和未覆盖范围。
- 不回显 Token、密钥、Cookie、真实用户数据或内部敏感地址。

若当前没有代码仓库或无法访问项目材料，不虚构项目现状：基于已知约束给出条件化候选方案并标注适用前提；证据足以选型时进入解决方案或否决出口，仍需调查时走验证出口，只有用户持有的信息才走澄清出口。

输出：项目现状、可复用能力、不可违反的约束、证据缺口及其是否阻塞决策。

### 第 3 步：生成候选

目标：生成差异真实、规模可控的候选，而不是同一方案的措辞变体。

先执行减法扫描：

| 方向 | 检查问题 |
| --- | --- |
| 不做 | 现有兜底是否已足够，问题是否暂不值得解决？ |
| 删除 | 删除冗余逻辑能否消除问题？ |
| 合并 | 合并重复职责能否降低分歧或维护成本？ |
| 复用 | 现有模块、配置、工具或流程能否直接覆盖？ |
| 回滚 | 回到已验证状态是否比新增机制更有效？ |
| 约定替代 | 文档、配置或流程约定能否达到同一目标？ |

六个方向都必须被覆盖，但允许合并判断，不要求逐项展开或展示内部推理。即使全部不成立也需一行留痕说明已覆盖；输出中只保留会影响候选选择的减法结论及证据，减法不能命中目标时说明具体差距。

候选要求：

- 至少包含 1 个最小改动候选。
- 简单问题允许只有 1 个候选；存在实质取舍时给 2~3 个。
- 每个候选写清：
  - **解决机制**：通过什么因果机制命中目标，不只写“增加 / 优化 / 建设”。
  - **关键改动**：涉及哪些模块、职责、流程、数据、接口、配置或约定；无法定位具体文件时说明待落位范围。
  - **运行方式**：主要流程、状态变化、调用或数据流，以及关键失败如何处理。
  - **复用与边界**：复用什么既有能力，明确不改什么、不会覆盖什么场景。
  - **实施与验证**：依赖前提、改动规模、实施顺序、验收标准和失败回退。
  - **收益与代价**：立即与延迟、局部与整体影响。
- 明确“牺牲什么、换来什么”，以及该取舍只在什么条件或阶段成立。

### 第 4 步：八问审查

目标：淘汰不对症或不值得推进的候选。

先单独执行问 1。结论为 `淘汰` 时立即停止评估该候选；为 `待验证` 时暂停并保留候选及验证条件，不等同于淘汰。只有 `通过` 才继续问 2~8。

| 问题 | 判定要求 | 允许结论 |
| --- | --- | --- |
| 1. 对症性 | 候选动作逐项命中核心目标和成功判据，且落地后可验证 | `通过 / 淘汰 / 待验证` |
| 2. 必要性 | 不做的代价成立，且没有足够的更轻替代 | `必要 / 暂不必要 / 淘汰` |
| 3. 通用性 | 先判定特例或共性，再选择局部修或通用建设 | `特例-局部修 / 共性-通用建设 / 过度泛化` |
| 4. 复杂度 | 新概念、状态、分支和维护约定可控；减法无法等价替代 | `低 / 中 / 高`，并说明扩散条件 |
| 5. ROI | 当前时间窗内的收益覆盖开发、回归、维护和故障成本 | `高 / 中 / 低 / 负` |
| 6. 一致性 | 与现有架构、术语、用户决策和模块职责不冲突 | `一致 / 可修正冲突 / 淘汰` |
| 7. 安全与隔离 | 未扩大敏感数据、权限、高副作用通道或隔离破坏；风险有门槛和审计 | `无新增风险 / 受控可接受 / 淘汰` |
| 8. 整体净效应 | 问题在整体上被真正解决，而非转移、跳过或掩盖到下游、他人或未来；解决后未净引入更多问题（问 1 看是否命中目标，本问看目标达成后问题是否被搬运或制造，区别于问 5 单项成本、问 6 冲突、问 7 安全） | `整体解决 / 显式缓解可接受 / 淘汰` |

问 1 必须单独覆盖；只有通过问 1 的候选才继续覆盖问 2～8。展开深度随风险和不确定性调整。每个结论绑定证据地图中的证据或明确标注 `[未验证]`，不要求为了章节顺序重复证据。

问 2～8 的关键前提为 `[未验证]` 时，该候选尚未通过八问，不得用附带假设的确定结论替代；暂停该候选并继续评估其它候选。没有候选通过时，能安全调查的缺失走验证出口，只有用户持有的范围、价值或授权缺失走澄清出口。非关键未知可作为限制保留，但必须说明不影响选型的理由。

状态迁移：

- 问 1 为`待验证`：暂停该候选并继续评估其它候选；若没有候选通过，走验证出口。
- 问 6 为`可修正冲突`：修正候选后重新执行问 1、问 6 及受修正影响的其它问题；无法修正则淘汰。
- 问 8 为`显式缓解可接受`：候选未整体解决但已显式声明为症状缓解、后续项或主动不做，且用户认可其代价——可推荐，但必须把这部分未解决内容记为可检索债务：为何走此捷径（放弃的更完整做法与换得的收益）、当前上限（在什么规模或条件内成立，越过即失效）、升级触发条件（出现什么信号就必须换成完整方案）；三要素缺一不当作整体解决，也不允许用“遗留问题、后续再说”含糊带过。
- 问 2～8 任一项为`淘汰`：记录确定性原因，不进入推荐。
- 问 7 的风险需要用户缩小范围或补充授权：触发 `CHECKPOINT / STOP`；风险本身无法降至可接受则直接淘汰，不交由用户用收益覆盖。

以下结论直接映射为淘汰：问 2 `暂不必要`、问 3 `过度泛化`、问 5 `负`、问 6 `可修正冲突`但修正后仍冲突、问 7 风险无法降至`受控可接受`、问 8 伪解决（未整体解决且未显式声明，或净引入问题多于所解决问题）。问 4 为`高`或问 5 为`低`时不自动淘汰，但必须由明确收益、不可替代性和回退方案共同证明可接受，否则淘汰。

若所有候选均被淘汰，不循环修饰方案，也不强行选“最不差”的一个：淘汰依据充分时走否决出口；仍有可消除的不确定性时走验证出口。

### 第 5 步：收敛与输出

目标：优先交付用户可直接评审和落地的解决方案；审查结论用于证明方案，而不是替代方案。

解决方案出口必须按以下优先级组织：

1. **问题定义**：用不超过 4 个要点说明待改变状态、核心目标与成功判据、关键约束和本次边界；不重复完整分析过程。
2. **推荐方案**：先用一句话说明选什么、如何解决核心目标、为什么现在选它。
3. **方案设计**：展开解决机制、关键改动、职责或流程、状态或数据变化、复用点、边界及失败处理。技术问题应尽量落到真实模块、接口、配置或文件；非技术问题落到角色、流程、规则和治理机制。
4. **实施计划**：按依赖顺序列出可执行步骤、影响范围、确认点和交付物；区分当前实施与后续可选项。
5. **验收与回退**：给出成功判据、测试或指标、观察窗口、失败触发条件和回退操作。
6. **取舍依据**：简要对比候选，说明牺牲什么、换来什么以及不选其它候选的原因。
7. **八问摘要**：逐问给结论和关键证据，低风险项可压缩；不要在方案设计之前展开长篇审查。
8. **风险与不做事项**：列出残留风险、不成立前提和本次明确不做的内容；若问 8 判为显式缓解，按可检索债务列出被转移或遗留的问题及其“为何走此捷径 / 当前上限 / 升级触发条件”。

问题定义只用于锚定方案，不得展开成主体；方案设计与实施计划的合计篇幅原则上应大于问题定义、审查与证据摘要的合计篇幅。输出深度随问题复杂度调整；简单问题可合并章节，但不得把推荐方案压缩成“决策 + 后续条件”。复杂或高风险问题必须保留证据、冲突、检查点和回退的可审查性。

## 失败处理

| 触发条件 | 一线处理 | 仍无法解决时 |
| --- | --- | --- |
| 用户持有的目标、价值排序、范围或授权不清 | 默认归并为最多 3 个关键问题；独立安全或不可逆取舍可分轮询问 | 走澄清出口并停止 |
| 项目文件、命令或环境不可用 | 记录失败位置和缺失范围，使用现有证据继续 | 能形成条件化方案则输出并标注待落位项，否则走验证出口 |
| 证据冲突 | 比较来源、时间、覆盖范围和复现条件，暂停依赖该结论的候选 | 有其它候选则继续；否则降级为 `[未验证]`并走验证出口 |
| 单个候选问 1 为待验证 | 保留候选与缺失证据，暂停后续八问 | 可评估其它候选；无候选通过时走验证出口 |
| 单个候选问 1 为淘汰 | 记录证据并淘汰 | 有未评估候选则继续；否则按“所有候选被淘汰”处理 |
| 候选在问 2~8 被淘汰 | 记录淘汰原因 | 不进入推荐 |
| 所有候选被淘汰 | 区分确定性否决与证据不足 | 前者走否决出口；后者走验证出口 |
| 发现重大安全、越权或隔离风险 | 缩小暴露面并增加鉴权、隔离、审计或确认门槛 | 需用户授权则触发检查点；风险无法消除则淘汰 |

## 输出模板

按实际出口选择一种，不同时输出全部模板。

澄清出口：

```markdown
- 当前问题：<去方案复述>
- 已知事实：<...>
- 阻塞决策的缺失：<为什么会改变方向>
- 需要确认：<默认最多 3 个归并问题；独立安全或不可逆取舍必要时分轮>
```

验证出口：

```markdown
- 当前判断：<证据不足 / 无候选通过>
- 当前候选方向：<候选及其成立前提；说明当前更倾向哪一方向>
- 已执行验证：<动作、结果、覆盖范围；未执行写“无”>
- 依据与缺口：<事实、推断、未验证项>
- 下一最小动作：<尚需执行的动作、成本、预期输出>
- 选型门槛：<什么结果选择哪个候选、否决哪个候选>
```

否决出口：

```markdown
- 核心目标：<目标 + 成功判据 + 验证方式>
- 结论：推荐不做 —— <直接依据>
- 淘汰原因：<候选未通过的关键问题与证据>
- 当前替代：<已有兜底、维持现状或无需建设的轻量动作>
- 重新评估条件：<什么变化发生后值得重新进入方案设计>
```

解决方案出口：

```markdown
## 问题定义
- 待改变状态：<当前状态与目标差距>
- 核心目标：<目标 + 成功判据 + 验证方式>
- 关键约束：<不可违反的约束>
- 本次边界：<解决什么 / 不解决什么>

## 推荐方案
<一句话说明选什么、如何命中目标、为什么选择它>

## 方案设计
- 解决机制：<方案如何产生目标结果>
- 关键改动：<模块 / 职责 / 流程 / 数据 / 接口 / 配置>
- 运行方式：<主流程、状态或数据变化、关键失败处理>
- 复用与边界：<复用能力、影响范围、本次不覆盖内容>

## 实施计划
1. <步骤、影响范围、依赖、确认点和交付物>
2. <...>

## 验收与回退
- 验收：<用例 / 指标 / 观察窗口 / 通过门槛>
- 回退：<触发条件、回退操作和恢复状态>

## 取舍与审查
- 候选取舍：<收益、代价、不选其它候选的原因>
- 八问摘要：<逐问结论 + 关键证据>
- 风险与不做事项：<残留风险、不成立前提、明确不做>
- 显式缓解债务：<仅问 8 为显式缓解时列出：为何走此捷径 / 当前上限 / 升级触发条件；否则写“无”>
```

## 反例黑名单

- 不把“加缓存、上消息队列、加抽象层”直接写成核心目标。
- 不把用户的核心动作偷换成相邻问题（如“及时停止”换成“判断闭合”）；复述须能逐词回读对齐原话。
- 不在问题复发时停在最先想到的表层原因反复打补丁；沿证据追到可控根因，或如实标注证据不足只做症状缓解。
- 不把问题转移、跳过或掩盖到下游、他人或未来当作解决。“显式缓解”只允许在用户认可代价时保留部分未解决问题，仍须通过安全与整体净效应审查，并记为带“为何走此捷径 / 当前上限 / 升级触发条件”的可检索债务；缺三要素或只写“遗留、后续再说”不算显式缓解，净引入更多问题的候选也不能靠标注缓解获得推荐。
- 不在可直接修复的明确 bug 上强制输出完整设计报告。
- 不因缺少所有理想证据而停止；先判断缺失是否真的改变决策。
- 不把“两处证据”机械应用到用户偏好、价值判断或低风险事实。
- 不把候选未通过审查解释为必须反复修改到通过。
- 不为形式完整固定输出多个候选、六项减法全文或冗长哲学章节。
- 不用“未来可能用到”证明通用机制的必要性。
- 不虚构仓库现状、运行数据、历史决策或外部依赖。
- 不在安全边界不明确时默认执行高副作用操作。
- 不把敏感信息写入方案、日志、缓存、报告或示例。
