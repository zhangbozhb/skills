# 沟通话术改写

帮助用户在不改变事实和核心诉求的前提下，把短消息或口头表达改得得体、清晰、有效，并说明关键调整理由。

## 适用边界

### 应使用

- 改写发给领导、同事、下属、客户、合作方或亲友的短消息
- 调整请求、拒绝、道歉、提醒、协商、通知、谈判等话术
- 根据沟通对象调整语气、信息顺序和术语尺度
- 对上一版话术提出“再委婉点”“缩短”“删掉这句”等追改

### 不应使用

- 技术方案、设计文档、周报、总结、复盘等长篇正式材料的结构化评审
- 纯翻译、语法校对或知识问答，且不涉及沟通策略
- 代写欺骗、冒充、威胁、骚扰、操纵或规避责任的话术

若请求包含不当目的，不优化其说服力；简短指出风险，并提供诚实、尊重、可核验的替代表达。

## 工作流

### 1. 确定输入

识别四项信息：

- **原话或事实要点**：需要改写的内容，或用户已提供、足以起草话术的事实
- **场景**：沟通发生在什么情境
- **对象**：对方的身份、关系和技术背景
- **目的**：希望对方理解、决定或采取什么行动

按以下顺序处理缺失信息：

1. 无逐字原话但已有事实要点和明确目的：直接起草，将这些要点作为事实基线，不虚构“原始话术”或诊断不存在的原句。两者都缺少且上下文不可恢复时，只询问需要表达的内容。
2. 原话完整，场景、对象或目的可从语义可靠推断：直接执行，并在【场景】或【对象】后标注“（推断）”。
3. 无法推断但不影响改写：使用“日常沟通 / 平级同事”作为默认值，并标注“（默认）”。
4. 不同理解会导致相反表达或明显风险：最多询问一个决定性问题，不同时追问多项信息。

不得仅因用户未说明技术背景，就把所有对象视为技术同事。先依据对象和原话判断；无法判断时，保留必要术语并补一句通俗解释。

### CHECKPOINT：需要用户确认

当歧义会改变责任归属、承诺范围、具体金额、法律含义或公开口径时，必须先提出一个决定性问题并停止改写。用户确认后再继续，不得用默认值替代。

### 2. 提取事实与约束

先区分以下内容：

- **已知事实**：人物、事件、原因、日期、承诺和结果
- **核心诉求**：必须传达的信息和希望达成的目的
- **情绪与关系**：原话中的态度，以及双方关系需要的语气
- **不可新增信息**：原话未给出的排期、责任人、处理动作、结果和承诺

事实优先级高于表达完整度。不得为了让话术“更落地”而编造日期、进度、原因、措施、权限或承诺。

### 3. 诊断原话

只指出会影响当前沟通目标的至多 3 个主要问题，不机械凑齐类别；原话已清楚得体时允许没有问题，保留原话或只调整用户明确要求的部分：

- **结构**：结论滞后、重点散乱、因果不清
- **语气**：强硬、抱怨、说教、卑微或过度客套
- **立场**：忽略对方关切，容易被理解为甩锅或命令
- **内容**：缺少必要事实、行动项或可确认的请求
- **表达**：语病、歧义、行话过多或语体不一致

分析必须指向原话中的具体词句，并说明它可能造成的沟通影响。对事不对人，不给用户贴标签。

### 4. 选择表达策略

根据问题选择最少且最匹配的方法：

- 需要快速决策或对上汇报：**结论 → 影响 → 原因 → 方案/请求**
- 需要解释立场或说服：**观点 → 理由 → 例证 → 重申**
- 需要处理情绪、冲突或道歉：**承接感受 → 客观事实 → 需要/责任 → 明确请求**
- 需要说明个人贡献或复盘事件：**情境 → 任务 → 行动 → 结果**

不要为了展示方法论而套用不相关框架。通常只写一个方法名称和一句应用说明。

### 5. 重组话术

按对象调整：

- **领导**：结论先行，说明影响，提供可决策的方案或请求
- **下属**：目标明确，说明标准、支持和反馈方式
- **平级同事**：平等协商，说明共同目标和具体配合事项
- **客户/合作方**：先承接影响；己方服务异常或已给对方造成不便时先致歉，再说明已知事实、已确认的处理动作和同步节点；未知项不补写
- **亲友**：自然真诚，减少公文语气，优先维护情感连接

按受众调整术语：

- 技术受众可保留必要术语，但避免无关细节
- 非技术受众用通俗表达保留已知含义。例如，“RPC timeout”改为“系统间请求未在规定时间内得到响应”；只有原话给出用户影响时，才说明数据显示或其它功能受影响
- 不确定受众背景时，采用“通俗结论 + 必要术语括注”，不要默认堆叠缩写

涉及行动、计划或承诺时，检查三项：

- **主体**：谁负责
- **时间**：何时完成或下次同步
- **结果**：届时能确认什么

仅对用户已经表达的行动或承诺补充 `【责任人】`、`【X 月 X 日 X 点】`、`【可验证结果】` 等必要占位符，并提醒发送前确认；占位符不代表已有承诺，不能用它新增处理动作或保证结果。承诺范围存在关键歧义时，回到 CHECKPOINT。

原话使用“尽快”“近期”“后续处理”等模糊承诺时，指出缺少时间边界。已有明确行动与期限承诺、仅缺具体值时可使用占位符；否则保留原承诺强度，在话术外建议用户确认时间，不擅自改成定时同步或保证完成。

### 6. 自检

输出前逐项检查：

- 是否保留核心事实和诉求，没有改变责任归属
- 是否新增了用户未提供的事实、承诺或时间
- 是否把术语解释或合理推测误写成已发生的影响、原因或措施
- 语气是否适合对象，术语是否符合对方背景
- 每个占位符是否确有必要，并明确提醒发送前替换
- 重组后的话术是否可以直接使用
- 分析是否精简，是否只解释关键改动

任一项不通过，先修正再输出。

## 输出规则

### 首轮

根据事实要点起草时，直接给出话术，必要时补一句表达理由，不套原话诊断模板。原话没有实质问题时直接给出可用话术；用户未要求只给结果时，可补一句“原话已清楚，无需实质调整”，不套问题分析模板。

原话只有 1-2 个主要问题时，使用精简结构：

```text
【场景】...
【对象】...
【目的】...

【重组后 v1】
...

【为什么这样改】
- ...
```

出现以下任一情况时，使用完整结构：用户明确要求详细分析；原话存在 3 个及以上相互关联的问题；需要比较多个表达策略。

```text
【场景】...
【对象】...
【目的】...

【原始话术】
...

【问题分析】
- ...

【改进方向与方法】
- 方向：...
- 方法：...

【重组后 v1】
...

【调整说明】
- ...

【沟通小贴士】（仅有可复用且与本次直接相关的经验时输出）
- ...
```

执行约束：

- 用户明确要求“只给改写结果”或“不要分析”时，仅输出可复制话术和必要的占位符提醒，不加版本标题或分析标签
- 精简结构中的【为什么这样改】只保留 1-2 条，仍需指出原话的具体问题
- 完整结构中的【问题分析】和【调整说明】各保留 1-3 条
- 【重组后】通常不超过 5-8 行，短原话可保持 1-2 句，不为满足行数补充事实；这是对可复制话术的限制，不是对整份回复的限制
- 一句话承载一件事，删除无意义铺垫和重复表态
- 默认只给一个版本；用户明确要求多个版本，或语气选择确实会改变沟通效果时，才提供 2-3 个版本
- 占位符后追加一句“发送前请补充：...”并列出缺失项
- 不使用表格、复杂排版或多级编号；用户明确要求正式格式时除外
- 本 skill 只生成话术，不发送消息；用户要求发送时，按实际发送能力的授权与确认流程另行处理

### 迭代

用户针对上一版提出增删、缩短、语气或措辞调整时，继承已确定的场景、对象、目的和事实，只输出：

继承前按用户最新补充核对事实。用户纠正日期、原因、责任或承诺时，同步修正所有受影响句子；助手上一版自行推测或补写的内容不能视为用户已确认事实。新旧信息仍有关键矛盾时回到 CHECKPOINT，不能靠保留旧版本来回避。

```text
【本次调整】...

【重组后 vN】
...
```

- `vN` 在当前版本上递增
- 用户要求“只给结果”时省略【本次调整】，只给新版话术和必要的占位符提醒；该要求优先于默认迭代模板
- 上一版内容可见但没有版本标签时，将其视为 v1，本次输出 v2
- 用户指定“回到 v2 再改”时，以 v2 为基准生成新版本，版本号仍接续当前最大编号
- 用户明确说“重新来”“另一件事”或给出独立的新沟通任务时重置为 v1；同一任务中的事实纠正、补充原话或换接收对象仍递增版本
- 若上下文中找不到上一版，说明无法可靠继承，并请用户贴出上一版；不得假装记得

## 反例黑名单

- 不把“需求改了多次”直接包装成甩锅，也不擅自改变责任归属
- 不用冗长分析淹没用户真正要复制的话术
- 不因追求礼貌而加入卑微、过度道歉或空泛客套
- 不在同一话题的追改中重复整套首轮分析

## 示例

**用户输入**

> 帮我跟领导说：项目要延期一周，主要是需求改了好几次。

**输出**

```text
【场景】项目延期汇报（推断）
【对象】直属领导（推断）
【目的】说明延期时长和主要原因

【重组后 v1】
领导，项目需要延期一周，主要原因是需求经过了多轮调整。

【为什么这样改】
- 将“改了好几次”改为中性表达，保留延期时长和原因，不新增开发安排、交付日期或承诺。
```
