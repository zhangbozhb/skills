# Agent / Harness 建设评估与指导

## 这个 skill 是什么

一套用于**评估和指导 agent 与 harness 建设**的思考框架 + 可勾选检查清单。它不产出业务代码，而是回答四类问题：

1. 这个 agent / harness 的建设，**缺口在哪、该往哪发力**？
2. 某个能力，应该做成**通用机制（harness）**还是**业务定制（策略）**？
3. 为什么"接了工具/MCP/skill 却仍然不是一个好 agent"？
4. 这个 agent 现在处在什么**成熟度**，离"能上线/能运营"差哪几步？

## 核心定义（所有判断的锚）

> **harness = agent 的操作系统。** 模型是 CPU——会推理，但无状态、不可信、不能直接碰真实世界。harness 是模型与真实世界之间的内核：管资源（上下文）、管 I/O（工具）、管权限（安全）、管进程（控制流）、管故障（可恢复）。
>
> **工具决定 agent"能做什么"；harness 决定 agent"能不能把事做对、做稳、做得安全、并且越做越好"。**

两条评判轴，缺一不可：

- **内部构造轴**：分层、异常、契约、安全——它"造得对不对"。
- **结果/任务轴**：端到端有没有解决用户的真实任务——它"办不办得成事"。
  内部很干净却办不成事的 agent，同样不是好 agent。**任务成功率是最终裁判**，内部判据是为它服务的。

## 何时使用

- 设计一个新的 agent，或评审现有 agent/harness 架构。
- **基于现有代码/实现审查其架构、流程、职责划分**（不是 code review——不看命名/格式/局部代码复杂度，只看架构级问题：分层是否塌陷、编排层是否被藏进 middleware/util、职责是否错位、流程/图结构是否过度复杂。见判据三与文末边界说明）。
- 判断"某个能力该做成通用 harness 机制，还是业务侧定制"。
- 排查"工具都齐了，agent 却不好用/不稳/不敢上线"。
- 需要给 harness 建设排一个**发力优先级**，或给出**成熟度评级**。

不适用：纯业务工具/MCP/skill 的具体实现；一次性问答；与 agent 架构无关的普通代码修改。

## 判据一：机制 vs 策略（共性与定制的本质分界）

来自操作系统设计原则 **mechanism/policy 分离**。这是回答"共性 vs 业务定制"的唯一锋利切法：

> **"怎么做到"的能力 = 机制 = 共性，沉到 harness；"具体定成什么样"的规则 = 策略 = 业务，做成配置/prompt/护栏。**

| 能力 | 机制（共性 · harness 做） | 策略（业务 · 必须定制） |
|---|---|---|
| 审批闸门 | 提供"某动作可拦截、可要求确认"的钩子 | 退款 > N 要审批 / 删除要二次确认 |
| 上下文注入 | 检索、裁剪、排序、spill/找回引擎 | 哪些数据源、哪些规则算"相关" |
| 截断/压缩 | 可预期、可找回的截断与摘要机制 | 优先保留哪些字段、什么算关键信息 |
| 控制循环 | 步数上限、停止条件、循环检测、重试/回滚 | 什么算"完成"、什么算"该停" |
| 权限沙箱 | 可写范围、网络策略、危险动作拦截开关 | 能写哪、能连哪、什么算危险 |
| 可观测 | trace/日志/回放/eval 骨架 | 什么指标算成功、拿哪些线上案例回归 |

**评估动作**：对争议中的每个能力问一句——"这是机制还是策略？" 通用机制需有复用依据，业务策略不应被硬编码为通用规则；项目约束以实际读取的规范为准，不假定存在特定 `AGENTS.md` 或条款。

## 判据二：异常优先（happy path 是少数派）

类比传统软件——正常代码只占一小部分，大部分在处理异常与兜底。**agent 更极端**，因为它比传统软件多一个失败面：

- 工具/外部世界会失败（超时、脏数据）——传统软件也有。
- **模型本身会"失败"**——幻觉、选错工具、参数编错、不知道停、被注入。这是新失败面。

好 agent 的工程重量必须压在失败处理上：

- **输入校验**：模型给的工具参数 = 不可信输入，按校验用户输入的标准校验（类型、范围、越权）。
- **失败分类差异化**：暂时性错误且确认可安全重试 → 有界退避；逻辑错（参数错）→ 把错误喂回模型自我修正；不可恢复错（越权/资金异常）→ 升级人工。副作用请求超时可能已经成功，应先查询操作状态或核对幂等保证；结果未知且无法安全重试时停止重放。**"全 catch 打日志"是坏味道。**
- **幂等与可回滚**：重试不能重复退款/重复下单。agent 里重试极常见，这是硬需求。
- **跨步事务（saga/补偿）**：多步业务流程中途失败，要能补偿已完成的副作用，而不是留下半完成状态。别只想着单步幂等，要想整条链的一致性。
- **兜底与降级**：工具挂了有无 plan B；模型卡住能否安全停在一致状态。

**评估动作**：审查时刻意只看"失败路径"——如果一个 agent 的设计文档/代码里 happy path 占了大头、异常处理草草了事，它大概率不能上线。

## 判据三：赢在"API 之上那层"（同样工具，差异巨大）

同样接一堆工具/模型，好坏差在 API 之上的工程。用软件工程经典视角逐层查：

1. **分层架构（纵向）**：推理层（模型）/ 编排层（harness）/ 能力层（工具）/ 世界层（真实系统）是否清晰？还是糊成一个大 prompt + 大 loop（等于 5000 行万能函数）？
2. **编排结构（横向）**：纵向分层之外的另一轴——**编排层内部怎么切分**。workflow 节点 / 主 agent / subagent 各自**功能单一、边界清晰、可独立理解**吗？还是主 agent 与 subagent 职责重叠、耦合成一坨（= 横向的"大 prompt + 大 loop"）？划分依据是否成立：每个 subagent / 节点为什么存在、吃什么输入、交付什么、和谁有依赖——说不清就是划分本身有问题，不只是代码乱。（编排是 agent 的主要代码，这一轴常是质量分水岭；与判据八多 agent 呼应。注意：评的是划分的**清晰度与内聚度**（机制），不替业务定"该切几个 agent"（策略，见判据一）。）
3. **数据结构决定一切**（Brooks）：agent 的"数据结构"= 状态与上下文的组织（任务状态、已确认事实、待办、证据）。**质量上限由此决定，不是由 prompt 措辞决定。**
4. **非功能性需求（NFR）**：延迟（可并行的工具调用是否并行）、成本（token = 内存+带宽，越干净越准）、体验（流式、可中断、进度可见）。
5. **并发正确性**：并行工具调用不只是提速——要判断哪些调用**有副作用、有顺序依赖、并行不安全**（如同时写同一资源）。只把并行当性能优化、忽略竞态，是隐藏 bug。
6. **接口契约**：工具 schema + 描述 + 错误信息 = API 契约，同时是给模型读的 prompt。契约含糊 = 模型误用。

**代码分层 ≠ Graph 分层**：逻辑层用于组织职责，可以很深；Graph / Subgraph 是运行时控制边界，只承载拥有独立流程、状态与恢复语义的单元。不要因为多一层目录或抽象，就机械加一层 Graph。

**Graph 边界测试**：一个单元成为 Graph / Subgraph 必须同时具备——无法由单个节点清晰承载的独立多步控制流；自己的状态所有权或失败/恢复边界；稳定输入输出契约与单一责任。三者缺一即优先降级为 Worker、Node、Tool 或 Domain Service（Worker 是受父级编排、可复用、可独立测试的执行角色，可实现为函数、工具、subgraph 或 agent——确定性能力别一律 agent 化）。独立 trace、eval、复用或团队维护只能增强理由，不能单独证明需要 Graph。

Graph / Subgraph / Node / Worker 是**通用架构角色**，不特指 LangGraph；完整角色定义、运行时映射与逐层审查流程见 [代码分层与 Graph 分层专项审查](references/graph-code-layering-review.md)。当目标包含多层 Graph / Subgraph / Worker、逻辑层超过三层、编排分散在 middleware 与 agent 中，或无法判断某能力应落在哪种实现形态时，必须展开该专项审查，不要只凭 Graph 层数或目录名称下结论。

**结构复杂度是设计合理性的反向信号**：一个流程/图的实现越绕、越难讲清楚，往往越说明设计本身没理顺——复杂度是征状，设计缺陷是病根。注意区分两种复杂度：**局部工艺复杂度**（单函数圈复杂度、嵌套深度、代码行数）归 code review，不在本 skill；**结构/流程复杂度**（图/编排整体绕不绕、职责散不散、能不能讲清）是架构信号，属本 skill。反向信号包括：

- **一句话讲不清主流程**：说不清"入口→关键阶段→退出"的主干，要靠一大堆特例才能描述，多半是流程没收敛、边界没划对。
- **Graph 层数 / 节点数 / 分支数明显超出任务本身的复杂度**：任务不复杂但图很复杂，是设计在代偿——常见于逻辑层被机械映射成 Graph（判据一/边界测试），或缺少收敛机制（判据五）靠加分支硬兜。
- **控制流跨层缠绕**：跨级调用、跨级写状态、阶段判定散落在 prompt / middleware / Graph 多处（谁说了算不唯一），复杂度来自职责错位而非任务本身。
- **改一处牵动多处**：加一个能力要同时动多个 Graph / 节点 / 状态字段，说明模块耦合、职责没有单一归属。

判定要领：**先问"这个复杂度是任务固有的，还是设计造出来的"**。任务固有的复杂（多阶段业务、真实分支）应体现为清晰的独立控制域；设计造出来的复杂（代偿、耦合、错位）才是缺口。不要因为"看起来复杂"就扣分，也不要因为"能跑"就放过——复杂度异常时，回到判据一（机制/策略错位）、本判据的边界测试与正向定位、判据五（收敛机制缺失）定位病根。

**评估动作（从代码征状反推架构）**：架构长在代码里，代码实现的混乱往往是架构缺陷的投影。审查时把下面三个高信号当抓手，**从代码征状反推架构问题**（结论是架构，代码只是证据）：

- **单一处理里堆满 `if` 特例 / 例外分支** → 职责或抽象边界没划清：多半是把本该外置的策略（业务规则）塞死进了机制里（见判据一），或一个函数扛了多层职责。
- **职责在模块/函数间来回渗透、没有单一归属** → 分层塌陷、编排层缺失（大 prompt + 大 loop 的另一种表现）。
- **一个"名分低"的组件承载了远超其名的职责**（如 middleware / 拦截器 / 装饰器 / util / hook 里长出完整状态机、阶段判断、prompt 生成、子 agent 派发、特殊策略）→ **责任错位**：编排层被藏进了一个本该只做机制拦截的钩子里。警惕：**正因为钩子/中间件在判据一里是"正当机制"，它最容易被当垃圾场**，把编排与策略偷偷塞进去而躲过审查——看到"合规名义"的组件，更要翻开看它实际做了什么，不能凭名字放行。

**正向定位测试（防"编排层缺失"漏检）**：明确指认状态、阶段流转和退出判定由哪个模块或框架负责，并沿调用关系验证。职责有稳定归属、契约和测试时，不能仅因文件名含 middleware/util 或没有单独目录就判错；确认横切钩子同时控制业务阶段并造成控制权混杂时才记为责任错位。材料不足时记为未验证，不以补建一层作为默认修复。

注意区分：这里看的是"代码暴露了什么**职责/流程/分层**问题"，不是"代码**写得好不好看**"（命名、函数长度、重复、局部复杂度那类工艺问题归代码审查，见下方边界说明）。

## 判据四：软件工程生命周期映射（查漏用）

一个好 agent = 把成熟软件工程每个阶段，在"模型不可信 + 依赖不稳定"约束下重做一遍。工具只是其中一格。

| 软件工程阶段 | 好 agent 的对应 | 差 agent 的表现 |
|---|---|---|
| 需求/规格 | 明确"任务完成"的定义与成功判据 | 目标模糊，早停或空转 |
| 架构设计 | 推理/编排/能力/世界 分层，状态建模 | 一个大 prompt + 大 loop 糊到底 |
| 编码规范 | 工具契约统一、错误结构化、命名有语义 | 工具描述随意、错误只有字符串 |
| 防御性编程 | 校验模型输出、最小权限、信任边界防注入 | 无条件信任模型和工具返回 |
| 异常处理 | 失败分类 + 重试/降级/升级 + 幂等 + 补偿 | 全 catch 吞掉或直接崩 |
| 测试 | 任务做成可回放的 eval 用例集 | 靠人肉试，改一处崩三处 |
| CI/回归 | 线上失败沉淀成回归集，防 prompt 退化 | 每次调 prompt 都是赌博 |
| 可观测/运维 | 全链路 trace、可复盘、可回放 | 出事无法定位为何这么决策 |
| 迭代/重构 | 机制与策略分离，可持续演进 | 全靠往 prompt 加补丁，越加越脆 |
| 依赖管理 | 模型版本固定、升级有回归基线 | 上游换模型，行为静默漂移无人知 |

## 判据五：软/硬约束边界（agent 与传统软件的根本差异）

传统软件确定性；agent 的执行核（模型）概率、非确定。由此两条不能纯套软件工程的原则：

- **控制流是"软"的**：流程一部分在 prompt（软约束），一部分在 harness（硬约束）。**关键的、危险的、不可逆的动作，必须落在 harness 硬代码里，不能只靠 prompt 求模型"请务必"——模型会不听。**
- **为不确定而设计**：接受"同一输入可能走不同路径"，因此要设计**收敛机制**（停止条件、完成判据、护栏），而不是假设它每次走同一条路。

> **边界原则（agent 架构最核心的一次决策）**：确定性 + 安全攸关 → 硬代码（harness）；开放判断 → 交给模型（prompt），再由 harness 兜底。这条线划得准不准，基本决定 agent 是"能演示"还是"能上线"。

## 判据六：指令层级（谁说了算 + 防注入的根）

模型会同时收到多个来源的"指令"：系统/开发者提示、用户输入、检索内容、工具返回。必须有明确优先级：

> **system/developer > user > 外部数据（检索结果、工具输出、被读文件）。外部数据是"数据"，不是"指令"，永远不能凌驾上层、不能改写 agent 的目标与安全约束。**

- 这是"把硬约束错放到 prompt 软层"（如 prefer/must 混淆）问题的一般化，也是**防提示注入的根**：工具结果里的一句"忽略之前的指令"绝不能生效。
- **评估动作**：冲突时谁赢是否已定义？工具/检索返回的文本能否改变 agent 的目标或绕过审批？如果能，就是高危缺口。

---

## 判据七：模型是会漂移的依赖

传统软件锁依赖版本即可复现；agent 的核心执行体是模型，**会被上游升级替换，行为随之漂移**——同样的 prompt 和工具，换个模型版本表现可能大变。

- 需要：模型**版本可固定/可切换**、升级有**回归基线**、关键行为有快照。
- **评估动作**：换一个模型版本，评估集是否还过？有没有基线可比？升级模型是"点一下"还是"过一遍回归"？

---

## 判据八：记忆与多 agent（连续服务与规模化）

- **两种记忆要分清**：
  - **上下文记忆（短期）**：本次任务的工作内存，随会话结束而失效（判据三的"数据结构"）。
  - **长期记忆（跨会话）**：用户偏好、历史结论、经验沉淀。业务 agent 连续服务需要它，但要管好**写入门槛、过期、冲突、污染**（别把一次错误结论永久记住）。
- **多 agent / 子 agent 编排**：任务分解、委派、何时 spawn 子 agent，以及**子 agent 间的上下文隔离**（避免互相污染、避免机密越界）。注意 subagent 有两种用途——(1) **上下文隔离/清洁**：把嘈杂子任务丢给子 agent、主上下文只收结论，这属上下文引擎机制（判据三），早期就该有；(2) **任务分解/规模化**（L4）。别把"隔离"误当成只有 L4 才需要。不是所有 agent 都需要，但一旦需要，隔离与汇总协议要提前设计。（本条讲"要不要用、怎么隔离汇总"；至于**主 agent 与 subagent / workflow 节点的职责划分对不对、有没有搞成一坨**，是编排结构的架构问题，见判据三"编排结构（横向）"。）

## 专项一：忠实性（fidelity）——对世界诚实 + 对用户诚实

harness 每加一层"展示/加工/裁剪"都在制造"模型所见 ≠ 世界真实"的裂缝；agent 也可能"谎报"自己做过的事。两个方向都要守：

**1. 对世界诚实（工具结果忠实）**
- 任何叠加的展示/加工层必须**可追溯、可声明**：区分元数据与正文，保留原始数据的定位；摘要、裁剪等有损加工要声明损失，不能要求从摘要反推出完整原文，也不能用摘要代替精确操作的原始输入。
- 精确操作（编辑/diff/写入）必须落在**原始数据**上，不是加工后的展示文本上。
- 截断、编码回退、失败必须**显式标注**，不能把不完整结果伪装成完整结果。

**2. 对用户诚实（自我报告忠实）**
- agent 不得声称完成了实际没做/没验证的动作；失败、跳过、假设要如实说。
- 工具"看起来成功其实被截断/被拒绝"要能识别并上报，而不是顺着编一个成功结论。

> **"看起来做成了、其实没做成"是业务 agent 里最贵的 bug**——它同时来自工具不忠实和 agent 不诚实两处，必须分别防。

---

## 专项二：安全深化（业务碰钱和用户数据，这里比通用注入更致命）

在"最小权限 + 审批 + 防注入"之外，业务 agent 必须额外查：

- **密钥/凭证处理**：密钥不进上下文、不进日志、不回显给模型；工具在 harness 侧持有凭证，模型只见句柄。
- **数据外泄（exfiltration）**：能读敏感数据 + 能对外发送（网络/消息/外部 API）= 泄露通道。要在 harness 层切断"敏感读 → 对外写"的危险组合。
- **混淆代理 / 越权（confused deputy）**：agent 以自身高权限执行了本不该替用户做的操作。每个副作用都要绑定"代表谁、被谁授权"。
- **对外/不可逆动作确认**：发送、下单、删除、转账——确认或审批，且"这次批准 ≠ 下次批准"。
- **PII/合规口径**：脱敏、留存、可审计，按业务合规要求定制。

---

## 专项三：非确定测试——如何测试一个"非确定"系统（评估方法论）

agent 不能用传统"单次断言通过"来验收——同一输入可能走不同路径。方法：

- **多次运行看通过率**，而不是跑一次就下结论（关注稳定性，不只是最好那次）。
- **LLM-as-judge + 人工校准**：开放输出用模型评审，但要有人工抽检校准评审器本身。
- **离线数据集 + 在线监控 双轨**：离线保回归不退化，在线抓真实分布的新失败。
- **回归门禁**：把线上失败沉淀成用例，改 prompt/换模型/改 harness 前必须过；设不退化阈值。
- 评估到"测试/回归"一项时，这属于"怎么落地 eval 流程"的实现职责，超出本 skill 的评估边界——若仓库中存在专门的 eval/回归落地 skill，应转交给它承接，不要在本 skill 内展开 how-to。

---

## 专项四：反馈闭环（要真的成"环"）

好 agent 的改进不是一次性的，而是一条闭合回路：

> **线上 trace → 失败归因 → 沉淀数据集 → eval 复现 → 修复（prompt/harness/工具）→ 上线门禁 → 在线监控 → 回到 trace**

- **评估动作**：这条环断在哪一段？最常见是"有 trace 但不归因""修了但没进回归集"——下次照样复发。

---

## 成熟度分级（先给评级，再谈发力）

证据足够时先给级别；证据不足时明确缺口，不强行定级：

| 级别 | 名称 | 达到标准 | 结论 |
|---|---|---|---|
| **L0** | Demo | 仅 happy path 能跑；几乎无异常处理、无安全闸、无评估 | 只能演示 |
| **L1** | 健壮 | 有输入校验、失败分类、幂等/回滚、兜底；单跑稳定 | 能自用 |
| **L2** | 可信 | 最小权限 + 审批闸 + 信任边界/指令层级 + 忠实回报与自我诚实 | 敢碰真实副作用 |
| **L3** | 可观测可回归 | 全链路 trace + 失败沉淀 eval + 回归门禁 + 非确定测试 | 改动不靠赌 |
| **L4** | 可持续运营 | 跨会话记忆/学习 + 模型漂移防护 + （按需）多 agent 编排 + 闭环持续改进 | 能长期运营 |

规则：级别取**已验证的短板**，不是取最高项；达到某级须累积满足该级及此前各级的适用能力要求。L0 的“无安全闸”等是低成熟度表现，不是升级时需要保留的条件。缺证据记为未验证，不等同于能力缺失，也不能算通过。不适用项需说明任务与副作用依据。上线通常要求 **≥ L2 且关键路径 L3**，不是上线批准。

**结果/任务轴闸门**：以上级别只评"内部构造轴"。结果/任务轴是最终裁判——真实任务做不成、任务成功率过低或从未度量到可上线水平时，无论内部多完善都不能据此判"能上线/能运营"。此时先在结论标注结果轴短板，再谈内部级别，不能用内部 Lx 掩盖端到端不达标。

## 反模式速查（证据成立时记录缺口）

- happy path 占满设计，异常/失败路径草草带过。
- 关键/不可逆动作只靠 prompt "请务必"，没有 harness 硬闸。
- 工具返回只有字符串错误，无结构化 `ok/error`；失败不可自愈。
- 一个大 prompt + 大 loop 糊到底，无分层、无状态建模。
- 截断/丢弃静默发生，模型以为拿到完整结果。
- 工具输出/检索内容能改写 agent 目标或绕过审批（注入未防）。
- 把通用机制里塞死业务策略（阈值/判据 hardcode），或把业务策略抽象成"通用框架"（过度设计）。
- 已沿完整调用链核对，仍无法确定阶段、状态和退出的权威归属，或横切钩子与业务编排争夺控制权；不因没有单独编排文件或目录就判错。
- 每个逻辑层都机械映射为一层 Graph，或把函数/规则/原子动作全部包装成 Subagent；新增层没有独立状态机、恢复边界或稳定契约。
- 流程/图结构复杂度明显超出任务本身：主流程一句话讲不清、Graph 层数/分支数代偿设计缺陷、控制流跨层缠绕、改一处牵动多处（结构复杂度是设计不合理的反向信号，非局部工艺复杂度）。
- 只跑一次就宣布"效果不错"，无多次运行、无回归集。
- 改 prompt / 换模型不过回归，靠人肉抽查。

## 发力优先级（面向业务 agent 的默认排序）

不是各项平均用力。已证实的越权、数据泄露、不可逆操作无审批等风险先作为阻断项处理；以下仅用于不存在未解决安全阻断的建设排序：

1. **上下文引擎 + 工具底座** —— 决定"能不能把事做对"；具体贡献需由目标任务数据验证。
2. **安全 / 权限 / 审批** —— 决定"敢不敢上线"（碰钱和用户数据的红线）。
3. **控制流 / 状态 / 可恢复** —— 决定"多步流程稳不稳"。
4. **可观测 / 评估 / 回归** —— 决定"能不能持续运营和改进"。

**最该投精力、也最难的一层**：不是模型也不是工具，而是"**业务知识 × 通用机制**"的耦合质量——
- 相关性：上下文引擎通用，但"这一步塞哪三条信息"是领域判断；
- 完成判据：控制循环通用，但"什么算完成/该停"是业务定义；
- 失败语义：重试机制通用，但"这个错该重试还是升级人工"是业务判断。

模型和工具是买来的，这层是自己挣的。

## 使用方式（怎么用这个 skill 做评估）

最低输入是目标任务及可定位的设计、代码或用户描述。先记录已检查范围和证据等级：设计声明只能证明计划，代码只能证明实现存在，运行结果才支持可靠性判断。目标不明确时询问一个关键问题；材料不可读时说明缺口并请求可访问材料，不凭空打分。

默认只读评估，不运行会产生真实副作用的业务流程。只有设计描述时输出设计预评估和验证清单，不授予已运行成熟度；缺少关键运行证据时使用“暂无法定级”或明确限定已验证范围。

1. **定位问题类型**：设计新 agent / 评审现有 harness / 判断共性归属 / 排查不好用。
2. **先立结果/任务轴**：这个 agent 要端到端解决的真实任务是什么、成功判据是什么、有没有可度量的任务成功率/通过率证据（无法度量时也要写明"未度量"）。这是最终裁判，下面的内部判据都为它服务，不能只凭内部干净就下结论。
3. **再过内部构造轴**（判据一~八，再接专项一~四）：机制 vs 策略 → 异常优先 → API 之上那层 → 生命周期映射 → 软硬约束边界 → 指令层级 → 模型漂移 → 记忆与多 agent → 忠实性 → 安全深化 → 非确定测试 → 反馈闭环。
4. **打分卡逐项记录**，区分有、部分、缺、未验证和不适用。
5. **定成熟度级别**（L0–L4，取已验证短板）；证据不足时不给确定级别。
6. **输出结构化结论**（模板见下）。

**建议输出模板：**
- **一句话结论**：当前证据支持 Lx / 暂无法定级，主要卡在 ___；不得把设计预评估写成上线批准。
- **结果/任务轴结论**：端到端能不能办成事——任务成功率/通过率证据或"未度量"；内部再干净，这里不达标就不算好 agent。
- **成熟度评级**：Lx（证据与短板项：___）/ 暂无法定级（缺失证据：___）。
- **缺口清单**：逐条 = 现象 + 定位与证据等级 + 归类（机制问题 / 策略问题）+ 严重度 + 最小验证动作；未验证项单独列出。
- **高危项特别标注**：有没有把硬约束（安全/不可逆）错放到 prompt 软层；工具输出能否越权改写目标。
- **发力优先级建议**：安全阻断优先，其余按上面 4 档排序，给出下一步最小动作。

> **出口衔接**：本 skill 停在"该建什么 + 优先级"，不展开"具体机制怎么设计落地"。当缺口需要落地设计时，属于设计职责——转交方案设计类专项能力承接（带上缺口清单与优先级作为输入）；若无对应能力，则如实说明"落地设计超出本 skill 边界"，不在本 skill 内展开 how-to。

> **边界说明（与代码审查的分工）**：本 skill 审"代码暴露了什么**架构/职责/流程/分层**问题"——单一处理堆例外分支、职责跨模块渗透、流程/图结构过度复杂这类征状要**反推架构**（见判据三评估动作与"结构复杂度反向信号"），属本 skill 范畴。但**代码级工艺问题**（命名、函数长度、重复代码、单函数局部圈复杂度、风格）不属本 skill——转交代码审查类专项能力。复杂度按此切分：**结构/流程复杂度（图/编排绕不绕、职责散不散）看架构，归本 skill；局部工艺复杂度（单函数写得绕不绕）归代码审查。**一句话切分：**读代码是为判断架构，不是判断代码写得好不好看。**
