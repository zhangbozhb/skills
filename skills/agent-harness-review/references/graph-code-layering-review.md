## 何时展开

仅在出现以下任一情况时读取并执行：

- 目标包含多层 Graph、Subgraph、workflow、Worker 或 subagent。
- 逻辑层超过三层，团队争议每层是否都应成为 Graph。
- 编排职责分散在 middleware、agent、工具和普通服务中。
- 无法判断某能力应实现为 Graph、Worker、Node、Tool 还是 Domain Service。
- Graph 嵌套、共享状态或跨层控制使失败恢复和测试边界不清。

本 reference 是**审查方法**，不规定具体目录结构、框架 API 或最大 Graph 层数，也不替项目设计完整落地方案。

## 适用范围与运行时映射

本 reference **面向通用的状态化 Agent 编排**，不是 LangGraph 专属规范。文中的 Graph、Subgraph、Node、Worker 表示架构责任；只有目标项目使用 LangGraph 时，才映射到 LangGraph 的具体构造。

| 通用角色 | LangGraph 中的常见映射 | 其它实现中的可能映射 |
|---|---|---|
| Graph | `StateGraph` 编译后的顶层执行图 | 工作流、状态机、流程编排器 |
| Subgraph | 作为 node 组合或在 node 内调用的 compiled graph | 子流程、嵌套状态机、可复用 workflow |
| Node | Graph 中的 node function / agent node | task、step、handler、activity |
| Worker | function、tool、subgraph 或 agent | job handler、service、actor、worker process |
| Agent Worker | agent graph 或调用 agent 的 tool/node | 具备模型循环的隔离执行单元 |
| State / checkpoint | graph state 与 checkpointer 管理的执行状态 | workflow state、事件日志、持久化游标 |

使用规则：

- **跨框架通用**：职责内聚、Graph 边界测试、状态所有权、父子契约、失败语义、Worker 可测试性和 middleware 边界。
- **LangGraph 特有**：具体 StateGraph API、subgraph 调用方式、checkpointer 继承、namespace、interrupt、stream、replay 和部署行为。
- **其它运行时特有**：调度保证、事务语义、重放模型、状态一致性和远程调用限制。
- 不能因为项目使用了名为 `graph`、`node` 或 `worker` 的类，就直接认定其承担本 reference 中的同名架构责任；必须以实际控制流、状态和失败行为为证据。
- 涉及具体运行时能力或限制时，先确认框架与版本，再查当前官方文档或实测；本 reference 不提供跨版本 API 事实。

## 核心区分

| 概念 | 判定锚点 | 不代表 |
|---|---|---|
| 逻辑层 | 代码和业务职责的组织层次 | 必须对应运行时 Graph |
| 控制域 | 拥有独立流程、状态所有权和恢复语义的执行单元 | 一个目录或类 |
| Graph / Subgraph | 控制域的显式状态机实现 | 任意多步骤函数 |
| Worker | 受父级编排、可复用、可独立测试的执行角色 | 必然是 Agent |
| Agent Worker | 需要开放式推理、工具循环或上下文隔离的 Worker | 所有复杂任务的默认实现 |
| Node | 单个可观测、可重试或可 checkpoint 的执行单元 | 完整业务层 |
| Tool | 原子外部能力或副作用接口 | 业务编排容器 |
| Domain Service | 纯业务规则、校验、融合或计算 | Graph 节点的同义词 |
| Middleware | 与业务阶段无关的横切机制 | 隐藏工作流的容器 |

## 审查流程

### 1. 建立事实清单

从入口、Graph 构造、节点、Worker、middleware、状态定义和测试中收集证据，先记录实际行为，不凭文件名推断职责。

| 单元 | 代码位置 | 输入/输出 | 控制流 | 状态所有权 | 失败/恢复 | 副作用 | 调用者 |
|---|---|---|---|---|---|---|---|
| `<name>` | `<path>` | `<schema>` | 分支/循环/阶段/无 | `<fields>` | `<policy>` | `<actions>` | `<parent>` |

至少回答：

- 对外入口和最终输出在哪里？
- 全局阶段、局部阶段和退出条件分别由谁决定？
- 每个状态字段由谁创建、更新和消费？
- 每个副作用由谁授权、执行、重试和补偿？
- 哪些单元可以脱离父流程独立运行和测试？

在已读取的完整相关实现中仍无法指认责任归属，才作为架构缺口；缺代码、访问失败或仅有片段时记为未验证。不得用设计图替代实现证据。

### 2. 执行 Graph 边界测试

对每个候选单元逐项判断：

- [ ] **控制流（必需）**：有无法由单个节点清晰承载的独立多步流程、分支、循环或阶段流转。
- [ ] **状态/恢复（必需）**：有私有状态所有权，或独立重试、降级、补偿、审批、中断和恢复边界。
- [ ] **契约/责任（必需）**：能定义稳定且窄的输入输出契约，并且只有一个内聚责任。
- [ ] **增强证据**：需要独立 trace、eval、复用、版本、部署或团队维护。

判定：

- 三项必需条件全部成立：可以成为 Graph / Subgraph；增强证据决定其收益强弱。
- 任一必需条件不成立：优先作为 Worker、Node、Tool 或 Domain Service；若仍选择 Graph，必须给出无法使用轻量形态的反证。
- 不得仅因目录层级、命名、团队边界或“未来可能复杂”创建 Graph。

层数不是结论。Graph 很深但每层都是独立控制域，可以合理；Graph 很浅但所有流程塞在一个节点或 middleware 中，仍然是坏架构。

### 3. 选择最小实现形态

按最小充分能力选择，不从 Agent 开始倒推：

| 需求 | 优先形态 |
|---|---|
| 纯规则、转换、融合、校验 | Domain Service |
| 单个可重试/可观测步骤 | Node / Function Worker |
| 一次原子外部操作 | Tool |
| 固定多步、分支、恢复流程 | Workflow Worker / Subgraph |
| 开放式推理、动态工具选择、上下文隔离 | Agent Worker / Leaf Subagent |
| 跨领域端到端阶段与全局退出 | Application / Process Graph |

若选择更重形态，必须说明轻量形态缺少什么能力；说不清则判为过度设计。

### 4. 审查状态与控制权

逐层检查以下不变量：

- 每个状态字段只有一个明确所有者；共享读取不等于共享写入。
- 父层向子层传任务、约束、最小上下文和预算；子层向父层返回状态、产物、证据、置信度和错误。
- 子层不得直接修改祖先状态、决定全局阶段或绕过父层审批。
- 兄弟 Worker 不直接互相控制；依赖、汇总和冲突处理回到共同父级。
- 每层只有一个阶段流转和退出判定权威，不能 prompt、middleware 和 Graph 各判一次。
- 状态保存原始结构化数据；prompt 和展示文本按需生成，不作为恢复事实源。
- 大对象和产物优先保存引用及校验信息，避免在多层状态中复制。

发现跨层写入时，要求给出一致性、并发和恢复证明；没有证明即列为高风险缺口。

### 5. 审查 Worker 契约

每个 Worker 至少应明确：

- 名称和单一能力目标。
- 输入、输出及字段校验。
- 完成、部分完成、失败和可重试的语义。
- timeout、预算、并发和取消规则。
- 副作用及幂等键。
- 可见上下文和禁止访问的数据。
- 独立测试入口和 eval 成功标准。

Agent Worker 额外检查：

- 是否确实需要模型自主判断，而不是固定流程。
- 工具白名单和可调用范围是否最小。
- 私有消息是否隔离，父级是否只接收必要结果。
- 停止条件和最大循环是否由 harness 兜底。
- 模型失败是否会污染父级状态或导致虚假成功。

### 6. 审查 Middleware

Middleware 只应承载横切机制，例如鉴权、脱敏、trace、通用 schema 校验、限流和错误归一化。读取阶段以记录日志、按父级契约保存 checkpoint、触发通用预算或权限硬闸，不等同于拥有业务阶段决策权。

确认横切组件擅自承担以下业务编排决策、且控制权未在独立契约中明确归属时，判为责任错位；不能仅凭组件名称或观察到阶段字段下结论：

- 判断 planning、dispatch、checkpoint 或 finalizing 阶段。
- 生成阶段业务 prompt。
- 决定 Worker 类型、数量、顺序或完成条件。
- 聚合领域结果、执行置信度融合或特殊复核规则。
- 决定是否结束任务或跳回模型。

正确归属通常分别是 Application Graph、Domain Graph、Worker 契约或 Domain Policy。

### 7. 审查嵌套与部署边界

- 不设固定最大层数，但每增加一层 Graph 都要记录独立控制域证据。
- 没有私有状态和恢复价值的中间 Graph 应拍平为 Node 或普通组合代码。
- 深层 Graph 必须保持逐层输入输出，不允许跨级调用和跨级状态写入。
- 相同权限、版本、扩缩容和故障域通常使用本地组合。
- 只有发布、权限、SLO、扩缩容或团队所有权确实独立时，才考虑远程或独立部署边界。
- 运行时的持久化、namespace、interrupt、回放和并发限制必须以当前官方文档和实测为准，不在本 skill 中硬编码。

## 输出要求

专项审查结果并入主 skill 的缺口清单，每条至少包含：

```text
现象：
代码证据：
责任归属：
当前实现形态：
建议实现形态：
违反的不变量：
严重度：
下一步最小动作：
```

至少明确回答：

1. 逻辑层和 Graph 层是否被机械一一映射？
2. 每个 Graph 是否有独立控制域价值？
3. Worker 是否有稳定契约并可独立测试？
4. Agent Worker 是否存在过度 agent 化？
5. 状态、阶段、退出和副作用分别由谁拥有？
6. Middleware 是否承载了业务编排？
7. 整体结构复杂度（图层数、节点、分支、跨层耦合）与任务本身复杂度是否匹配，还是设计代偿造成的过度复杂？

## 反模式

- 用目录深度或组织层级决定 Graph 深度。
- 用固定“最多 N 层”替代逐层责任证明。
- Root Graph 了解所有 Worker 内部消息、工具和临时状态。
- 子 Graph 直接写 Root State 或决定全局退出。
- Worker 只有自然语言描述，没有输入输出和失败契约。
- 确定性流程包装成 Agent，仅为了统一形式。
- 远程化只是为了减少本地 Graph 层数，没有独立部署价值。
- 设计文档分层清晰，但实现中的状态机实际藏在 middleware 或 util。
