# 目标驱动工作流

本 skill 用于根据任务复杂度选择最低够用的执行结构：简单任务直接完成，线性任务使用线性 loop，复杂任务使用显式状态 graph 编排，并在每个节点内执行“收集上下文 -> 行动 -> 验证 -> 更新状态”的闭环。重点不是增加流程，而是减少目标漂移、重复争论、无证据改动和上下文切换。

用户不需要预先理解本 skill、填写完整表单或准确说出“长程任务”。模型应从自然表达和任务形态判断是否启用，先推断最小目标状态，再只确认真正影响方向的信息。

## 自然触发与交互入口

### 用户主动触发

最明确的方式是直接说“使用 `goal-driven-workflow`”。日常交流不要求记住 skill 名，以下表达也应视为触发信号：

| 用户习惯表达 | 识别出的需要 | 首个动作 |
| --- | --- | --- |
| “这件事帮我持续推进”“接下来都围绕这个目标做” | 建立长期主线 | 推断主目标、成功判据和当前阶段 |
| “先把主线理清楚”“帮我盯住目标”“别跑偏” | 防止目标漂移 | 用一句话复述主目标并整理当前节点 |
| “继续上次的工作”“接着往下做” | 恢复中断任务 | 先核对最新状态、未验证项和恢复入口 |
| “这个先记下来，别打断当前工作” | 管理旁路发现 | 放入旁路池并继续当前节点 |
| “先不要改，分析清楚再说” | 阶段隔离 | 进入诊断阶段，设置进入实现的门槛 |
| “做完记得验证”“不要只改代码” | 建立验证闭环 | 补齐成功判据和验证方式 |
| “先收口”“总结一下再继续”“哪些该保留或回滚” | 阶段关闭 | 进入验证或收口阶段 |
| “最近一直在反复改这个，帮我理一下” | 漂移救援 | 重建目标、决策和证据，不直接继续微调 |

### 模型自动触发

用户没有主动要求时，满足以下任一条件可直接启用：

- 任务明确需要跨会话、跨提交或多轮实验。
- 用户要求持续治理一个主题，并同时包含诊断、方案、实现和验证中的多个阶段。
- 同一主题在对话中反复出现必要性、效果或改动范围质疑。
- 当前工作不断被新发现打断，已经难以说明主线和下一步。

只有单个弱信号时不自动套用完整流程，例如“修改多个文件”本身不等于复杂任务。模型应先做复杂度判断，选择最低够用的执行拓扑，并在任务持续扩张时再升级。

### 复杂度前置判断

执行前先判断复杂度，不以文件数、步骤数或用户措辞单独定级。检查以下维度：

| 维度 | 低复杂度 | 提升复杂度的信号 |
| --- | --- | --- |
| 目标清晰度 | 结果和验收明确 | 目标冲突、成功判据未知或需要方案取舍 |
| 依赖拓扑 | 单动作或单一路径 | 存在分支、汇合、并行、循环或跨模块依赖 |
| 不确定性 | 实现和结果可预期 | 需要调研、实验、运行时证据或多轮试错 |
| 验证难度 | 可立即、确定性验证 | 依赖样本、指标、人工判断或观察窗口 |
| 风险与可逆性 | 局部、低副作用、易回退 | 生产写入、删除、权限、安全、外部通信或难回退 |
| 持续时间与状态 | 单会话可完成 | 跨会话、跨提交、等待外部条件或需要断点恢复 |

不做机械加权打分。按以下规则路由：

- 只有所有关键维度都低，才走直接路径。
- 存在单一路径上的中等不确定性或多个依赖步骤，走线性 loop。
- 出现分支依赖、并行汇合、多轮实验、跨会话状态或显著不确定性，走状态 graph。
- 出现高副作用、权限、安全、生产或难回退操作，至少走受控 graph，并增加人工检查点；收益不能抵消安全门槛。

复杂度是动态状态，不是启动时的一次性标签。发现新分支、连续失败、范围扩张或外部阻塞时升级；任务收敛为一个明确可验证动作时降级。

### 执行拓扑

- **直接路径**：`明确目标 -> 执行 -> 验证 -> 结束`。不创建目标卡、graph 或持久记录；若任务本来就明确且一次性，通常不触发本 skill。
- **线性 loop**：维护主目标、当前动作和验证结果，按单一路径执行。只有验证失败或出现新证据时回到诊断或方案，不预先构造完整 graph。
- **状态 graph**：将工作包建模为节点，将依赖、条件、回退和结束条件建模为边；维护最小共享状态、检查点和可恢复入口。
- **受控 graph**：在状态 graph 基础上，为高副作用节点增加用户确认、权限边界、幂等、审计和回退要求。

graph 是工作控制模型，不要求绘图、引入框架或创建额外文件。只有当显式节点和边能降低分支、恢复或验证成本时才使用。

### 连续性模式

执行拓扑解决“任务有多复杂”，连续性模式解决“从哪里开始”，二者独立判断：

- **新任务**：从复杂度判断和入口节点开始。
- **继续任务**：核对最新状态，从最近一个仍有效的未完成节点恢复。
- **恢复救援**：适合已经反复修改或状态混乱的任务；先重建事实、决策、节点状态和未验证改动，再决定继续、回滚或重新诊断。

### 短控制语句

用户可以在执行中用自然短句控制流程，模型应立即更新状态，不要求重新描述背景：

- “这个是主线”：将当前事项设为主目标，处理旧目标的完成、挂起或替换关系。
- “这个先放一边”：加入旁路池，不中断当前节点。
- “暂停，先对齐目标”：停止实现，回到启动阶段检查目标与成功判据。
- “继续”：从最近一个未完成且未失效的工作包恢复。
- “先验证”：停止新增实现，进入验证阶段。
- “收口”：检查成功判据、残留工作和旁路事项，给出本轮结论。
- “换目标”：关闭或挂起旧目标，建立新目标卡后再行动。

## 职责边界

使用本 skill：

- 任务需要跨多个阶段、多个提交、多轮实验或多个会话持续推进。
- 用户希望在日常多步骤工作中保持主线、隔离新发现或确保完成验证。
- 同一主题不断出现“是否有必要”“是否有效”“为何修改”等重复质疑。
- 工作中不断发现相关问题，主线容易被局部问题打断。
- 用户要求长期推进、目标管理、阶段规划、持续优化或系统治理。
- 需要协调诊断、方案、实现、验证和提交，但不应把它们混在同一步中。

不使用本 skill：

- 一次性信息查询、命令执行或边界明确的小修复。
- 用户只要求设计方案且尚未进入长程执行；使用方案设计类 skill。
- 用户只要求代码审查、安全审查、定义审核或 skill 优化；使用对应专项 skill。
- 任务虽需要专业能力，但路径单一、可立即验证、没有高风险或持续状态，不需要额外工作编排。

本 skill 负责工作编排，不替代专项能力：

- 目标或方案仍有实质取舍时，转交方案设计类专项能力。
- 已有 skill 需要优化时，转交 skill 优化类专项能力。
- 进入代码审查、安全审查或定义审核时，调用对应专项 skill。
- 专项能力的产出必须回填本流程的目标、决策、验证或旁路记录，不能形成独立主线。

## 核心状态

启用后只维护执行拓扑所需的最小状态。直接路径不保留工作状态；线性 loop 可只在当前对话或任务计划中维护；状态 graph 优先复用项目已有计划、进度或实验文档。没有跨会话恢复需要时，不为形式完整创建新文档。

### 目标卡

目标卡只保留会影响决策的信息：

```markdown
- 主目标：<要改变的状态，不写具体解法>
- 成功判据：<可观察结果、验证方式和通过门槛>
- 当前基线：<已知事实、指标或复现结果；未知则标记未验证>
- 范围：<本轮处理对象>
- 不做事项：<本轮明确排除的内容>
- 关键约束：<兼容性、安全、资源、时间或用户决策>
- 停止条件：<成功、否决、回滚或必须重新定目标的条件>
```

### 执行状态

- **复杂度与拓扑**：记录影响路由的关键复杂度信号，以及当前采用直接路径、线性 loop、状态 graph 或受控 graph。
- **当前阶段**：启动或恢复、诊断、方案、实现、验证、收口六选一。
- **当前节点集**：默认只有一个正在执行的节点；只有满足并行约束时才允许多个。每个节点必须有输入、动作、输出、验收和失败出口，并直接服务主目标。
- **节点状态**：复杂任务记录 `pending / ready / in_progress / blocked / completed / rejected`；简单任务不维护节点清单。
- **决策记录**：记录被采纳或否决的方案、依据及重新评估条件。
- **旁路池**：记录执行中发现但不阻塞当前目标的问题。
- **验证记录**：记录测试、实验、失败样本、结果和未覆盖范围。

## 不可违反的规则

1. 先判断复杂度，再选择最低够用的执行拓扑；不得用 graph 包装本可直接完成的任务。
2. 同一时间只维护一个主目标；新目标必须替换、合并或排队，不能静默并行。
3. 每个节点必须映射到至少一个成功判据；无法映射则进入旁路池或删除。
4. 诊断、方案、实现和验证可以快速衔接，但不得用实现代替诊断、用代码 diff 代替效果验证。
5. 代码或配置修改前必须建立与复杂度匹配的变更契约；直接路径可压缩成“目标 + 验证”，受控 graph 必须包含风险与回退。
6. 实现结果必须与变更契约双向一致：契约内每项必要改动都要落地（防缺失），每处实际改动都要能回溯到契约条目或成功判据（防越轨）；以重构或等价改写为目标时以行为等价为准，不得静默增删逻辑或改变行为。
7. 新发现默认进入旁路池。只有它是当前节点的阻塞项、必要前提或重大安全问题时，才能改变 graph 路由。
8. 新增机制前先检查不做、删除、合并、复用、回滚或约定是否足够。
9. 节点内 loop 必须有进展信号、验证条件和停止出口；没有新证据的重复不能算进展。
10. 没有证据证明收益的改动不得仅凭“可能有用”保留；应验证、回滚或明确标为待验证。
11. 节点和阶段必须满足出口条件后才能流转；不能因“已经改了很多”而视为完成。
12. 用户的新指令改变主目标、成功判据或范围时，先更新状态和路由，再继续执行。
13. 不把流程本身当成产出。低复杂度任务压缩流程，只有 graph 任务才展开持久记录。

## 执行引擎：外层 Graph 与节点内 Loop

### 外层 Graph

状态 graph 用于控制复杂任务的全局结构：

- **State（状态）**：只保存路由和恢复必需的信息，包括目标、成功判据、复杂度、节点状态、关键证据、决策、阻塞和验证结论；大段原始材料按需读取，不持续堆入状态。
- **Node（节点）**：一个节点只承担一种职责，并声明输入、动作、输出、验收、失败出口和副作用。节点完成只提交状态增量，不重复改写整个任务历史。
- **Edge（边）**：根据已验证状态决定下一步，可流向完成、下一节点、重试、重新诊断、回滚、等待用户或终止。路由条件必须可判定，不能只写“视情况继续”。
- **Checkpoint（检查点）**：在跨会话、外部等待、高成本步骤和高副作用动作前后保存可恢复状态。恢复时从检查点核对现实状态，不盲目重放已完成动作。

graph 设计约束：

- 默认主干是“诊断 -> 方案 -> 实现 -> 验证 -> 收口”，但入口和边由当前状态决定，不要求每次从头顺序执行。
- 只有彼此独立、输入稳定且汇合规则明确的节点可以并行；汇合后必须统一验证冲突、遗漏和整体成功判据。
- 失败只回退到受影响的最近节点，不无条件重跑整个 graph。
- 可能被重试或恢复的副作用节点必须可安全重入；无法保证幂等时，在执行前设置人工检查点。
- graph 必须存在明确终止节点：完成、否决、回滚、阻塞等待或目标变更，禁止无限游走。

### 节点内 Loop

每个非平凡节点按以下反馈 loop 工作：

1. **收集上下文**：只加载当前节点完成所需的事实、约束和前序输出。
2. **选择动作**：选择能最大幅度减少当前不确定性或直接产生节点输出的最小动作。
3. **执行并观察**：运行工具、修改、实验或分析，保留真实结果和失败信息。
4. **验证进展**：比较动作前后状态，判断是否更接近节点验收条件。
5. **更新状态**：只写入新证据、决策、产物、阻塞和节点状态变化。
6. **条件路由**：
   - 达到验收条件：流向下一节点或汇合节点。
   - 有新证据且存在可行修正：继续当前 loop。
   - 失败原因属于上游假设或方案：回到诊断或方案节点。
   - 无新证据、重复失败或预算耗尽：停止 loop，转人工检查、回滚、阻塞或否决。

loop 不是“持续尝试直到成功”。启动前必须明确验收条件、进展信号、允许的副作用和停止条件；每轮都必须产生新证据、状态变化或可验证产物。长程执行应在检查点压缩上下文，只保留后续路由需要的事实与决策。

## 工作流程

以下阶段是状态 graph 的默认节点模板。直接路径只执行“行动 -> 验证”，线性 loop 只展开实际需要的阶段；不得为了形式完整强制经过全部阶段。

### 阶段 0：启动或恢复

目标：确定当前真实状态，避免依据过期上下文继续工作。

1. 读取用户最新指令、项目约束、现有计划和与主目标直接相关的状态。
2. 评估目标清晰度、依赖拓扑、不确定性、验证、风险和持续状态，选择最低够用的执行拓扑。
3. 判断是新任务、继续任务还是恢复救援；恢复已有目标、决策、节点和验证记录。
4. 检查工作区或当前产物，区分现实中的既有改动、已完成节点和未验证工作，修正过期状态。
5. 若成功判据缺失但可根据现有证据合理定义，直接提出并采用；只有不同答案会改变方向时才询问用户。
6. 直接路径立即执行；线性 loop 只维护当前动作；graph 创建或更新节点、条件边和检查点。默认只有一个节点为 `in_progress`，仅经依赖检查确认可并行的节点允许同时执行。

出口：主目标、成功判据、复杂度、执行拓扑、连续性模式和入口节点均明确。

### 阶段 1：诊断

目标：把现象转化为有证据的原因或待验证假设，不修改正式实现。

1. 收集能影响决策的最小证据：当前行为、基线、失败样本、调用链、日志、测试或实验结果。
2. 区分事实、推断和未验证假设，并写明什么证据会推翻关键解释。
3. 按对目标的影响排序问题，避免按发现顺序处理。
4. 将非阻塞发现放入旁路池；不得顺手修复。
5. 无法静态判断时，设计消除最大不确定性的最小实验。

出口：已定位主要原因，或形成可验证假设、最小实验和判定门槛。

### 阶段 2：方案

目标：只选择能命中原因和成功判据的最小方案。

1. 先执行减法检查：不做、删除、合并、复用、回滚或约定是否可以达成目标。
2. 每个候选说明解决机制、影响范围、验证方法、代价和回退方式。
3. 淘汰不能映射到失败原因或成功判据的候选。
4. 确定推荐方案并决定是否需要用户介入：
   - 默认直接采用综合权衡解决机制、影响范围、验证成本、代价与回退后最佳的候选方案并继续，不就方案询问用户；同等条件下优先更小、更易回退的方案。
   - 需要专业设计取舍时转交方案设计类专项能力，其产出回填为推荐方案。
   - 仅当取舍会改变主目标、价值排序、范围，或多个候选证据相当、模型确实无法抉择时，才向用户呈现推荐方案并请其决策；请求时必须给出明确推荐项作为默认。
   - 用户约 1 分钟内无响应，或该决策无需阻塞等待时，直接采纳推荐方案并记为假设继续，后续按用户反馈调整。
   - 例外：高副作用、不可逆、生产、权限或安全相关的取舍按受控 graph 的人工检查点处理，必须取得显式确认，不因超时自动采纳。
5. 形成变更契约：

```markdown
- 本次目标：<命中的原因或成功判据>
- 任务类型：<功能／新增、修复、重构／等价改写或其它；决定实现与验证的侧重>
- 必要改动：<文件、模块、配置、流程或文档，逐项列出以便实现后核对是否全部落地>
- 不改范围：<防止扩散的边界>
- 预期结果：<可观察变化；以重构或等价改写为目标时写“行为等价、无可观察变化”，并列出必须保持的行为与逻辑清单>
- 验证方式：<测试、实验、样本或指标>
- 回退方式：<失败时恢复到什么状态>
```

出口：方案已选定，变更契约完整，未决取舍已解决、已按推荐方案采纳并记为假设，或高副作用取舍已显式设为检查点。

### 阶段 3：实现

目标：严格按变更契约完成最小必要修改。

1. 将方案拆成可独立验证的节点，声明依赖、输入、输出、验收和失败出口。
2. 每次修改前复核当前文件和已有改动，不覆盖用户或其它任务的工作。
3. 仅对彼此独立且汇合规则明确的节点并行；有依赖关系时按 graph 边顺序执行。
4. 每个节点完成后立即对照变更契约做通用双向核对：契约“必要改动”是否逐项落地、有无功能或流程缺失（正向覆盖），以及本节点每处实际改动能否回溯到契约条目（反向回溯）；发现越轨的、与目标不一致的改动立即回退或拆入旁路池。
5. 再按本轮任务类型做该场景的侧重核对：功能／新增确认新行为与流程完整且未擅自扩展；修复确认命中根因且无回归；重构／等价改写额外核对“必须保持的行为与逻辑清单”，确认原有分支、边界处理和副作用未被静默增删。
6. 发现契约外问题时写入旁路池；只有阻塞当前节点时才更新路由或扩展契约。
7. 在节点内执行反馈 loop，完成后立即运行最接近改动的检查，不把所有验证积压到最后。
8. 更新节点和 graph 状态，但不因局部测试通过提前宣告主目标完成。

出口：契约内改动完成，局部检查通过，通用双向核对未超出范围、无必要项缺失，本场景侧重核对通过（如重构已确认行为等价）；否则回到方案阶段。

### 阶段 4：验证

目标：独立判断目标是否达成，而不是证明已有改动正确。

1. 先运行约定的测试、静态检查或复现步骤，再检查成功判据。
2. 先做各场景通用的契约双向核对，再按本轮任务类型补该场景的专项侧重，不因测试通过而跳过：
   - **通用（各场景都做）**：缺失——契约“必要改动”和成功判据是否全部落地，有无功能或流程未实现；越轨——是否存在无法回溯到契约条目、与目标不一致或不合理的额外改动。
   - **功能／新增侧重**：实现是否与新设计一致，预期的新行为、分支和流程是否完整，不缺步也不擅自扩展。
   - **修复侧重**：是否命中根因而非仅压制现象，并确认相关既有行为无回归。
   - **重构／等价改写侧重**：以行为等价为准，逐项核对“必须保持的行为与逻辑清单”，通过 diff、测试或前后对比确认原有分支、边界和副作用未被静默增删；无对照基线时补建后再判定。此侧重不适用于以改变行为为目标的场景。
3. 实验类工作使用实验记录：

```markdown
- 实验标识：<名称或版本>
- 固定条件：<代码、环境、数据集、模型、prompt/skill 和配置>
- 唯一变量：<本次只改变什么>
- 预期结果：<变化方向和门槛>
- 实际结果：<指标与关键样本>
- 覆盖范围：<已测与未测>
- 结论：<保留、回滚、继续验证或否决>
```

4. 多变量同时变化时，不把结果归因给单个改动；补做隔离实验或降低结论强度。
5. 失败时先判断是方案无效、实现错误、实验不可比还是证据不足，再决定回滚、修复或重新诊断。
6. 验证结论必须包含未覆盖范围，不能以单个成功样本代表整体有效。

出口：成功判据已达到，通用核对无缺失与越轨，且本场景专项侧重通过（如重构已确认行为等价）；或有充分证据否决方案并完成回滚；或明确进入下一轮诊断。

### 阶段 5：收口

目标：让本轮工作可追溯、可继续、可停止。

1. 汇总目标、必要改动、验证结果、关键决策和残留风险。
2. 提交前确认提交内容只服务一个清晰目的，并遵守项目提交规范。
3. 处理旁路池：
   - 删除已失效或低价值事项。
   - 合并重复事项。
   - 只提升与后续主目标直接相关且有证据的问题。
4. 明确下一状态：完成、进入下一目标、等待外部条件或重新诊断。
5. 只有主目标成功判据达成且无必需工作残留时，才宣告完成。

收口摘要：

```markdown
- 本轮解决：
- 关键改动：
- 验证结果：
- 未解决风险：
- 旁路事项：
- 下一状态：
```

## 漂移与中断处理

出现以下任一信号时，立即做一次目标检查，不继续机械执行：

- 连续两次质疑同一改动是否必要或有效。
- 当前工作无法说明对应哪个成功判据。
- 同一轮同时修改互不依赖的多个模块。
- 实现尚未验证，又开始设计新的优化。
- 新发现数量持续增加，主线工作没有关闭。
- 用户要求提交，但仍有关键改动未验证或无法解释。
- 当前节点重复执行相似动作，却没有新增证据或状态变化。
- 实际依赖和分支已经变化，但仍机械沿用原计划。
- 实现出现契约未列的改动，或契约必要项在实现中找不到对应落地。
- 重构或等价改写后行为发生可观察变化，或原有分支、边界、副作用被删减。

检查动作：

1. 重述主目标和当前阶段。
2. 重新评估复杂度、当前节点和 graph 路由，将当前动作映射到成功判据。
3. 无法映射则停止该动作并放入旁路池。
4. 若执行拓扑过轻或过重，升级或降级，不继续维护失真的状态。
5. 若成功判据本身已失效，返回阶段 0 更新目标卡。
6. 若同一方案被反复质疑或 loop 无进展，停止继续微调，路由到诊断、验证、人工检查或回滚。

## 沟通规范

- 不让用户承担流程管理工作：优先从自然表达推断目标和执行拓扑，不要求用户填写目标卡或选择阶段。
- 首次触发时只用一到两句话说明主目标、复杂度判断、当前节点和下一动作；graph 需要持久记录时再说明记录位置。
- 直接路径和线性 loop 默认隐藏内部状态，只在目标变化、复杂度升级、发现阻塞、进入验证或用户询问时展示。
- 执行中只汇报新证据、阶段变化、阻塞和影响决策的旁路发现。
- 用户给出明确执行要求时直接推进，不重复请求已经获得的确认。
- 需要用户决定时，只询问会改变目标、价值排序、范围或不可逆取舍的问题，并给出明确推荐项作为默认。
- 就方案询问用户时不阻塞等待：用户约 1 分钟内无响应即按推荐方案采纳并记为假设继续；但高副作用、不可逆、生产、权限或安全相关的确认必须等待显式回应，不因超时放行。
- 对“继续、先放一边、先验证、收口”等短控制语句，结合现有状态直接执行，不要求用户补充完整上下文。
- 最终答复优先说明是否达到成功判据、改了什么、如何验证和还剩什么。

## 失败处理

| 情况 | 处理 |
| --- | --- |
| 目标无法定义 | 汇总已知事实，并询问最多 3 个会改变方向的问题 |
| 缺少基线 | 先建立最小可复现基线，不直接优化 |
| 证据互相冲突 | 比较实验条件和覆盖范围，降低结论强度并设计隔离实验 |
| 复杂度判断偏低 | 保存当前结果，升级为线性 loop 或状态 graph，再补节点、分支和检查点 |
| 复杂度判断偏高 | 保留必要验收，降级执行拓扑并删除无价值的状态维护 |
| loop 无进展 | 停止重复动作，保留失败证据，转诊断、人工检查、回滚或否决 |
| graph 状态过期 | 以代码、环境和外部系统的现实状态为准重建当前节点，不盲目恢复 |
| 实现超出契约 | 停止扩散，拆出旁路事项；必要时回退契约外改动 |
| 实现缺失契约必要项 | 定位未落地的功能或流程，补齐实现或显式记为待办，不宣告完成 |
| 重构后逻辑丢失 | 对照行为清单或基线定位被删减的分支与副作用，补回或回滚，再重新验证等价 |
| 验证失败 | 区分实现错误、方案错误和实验不可比，再选择修复、回滚或重新诊断 |
| 外部条件阻塞 | 记录阻塞、已完成状态和恢复入口，不制造替代性忙碌 |
| 用户改变方向 | 更新目标卡、关闭或挂起旧工作包，明确新旧目标关系后继续 |

## 完成检查

启用本 skill 的任务只有同时满足以下条件才算完成：

- 主目标和成功判据没有被后续工作静默改变。
- 执行拓扑与任务最终复杂度匹配，没有遗留无价值流程或缺失必要控制。
- 所有正式改动都能映射到成功判据或必要约束。
- 变更契约的每项必要改动都已落地，无功能或流程缺失，且无与目标不一致的越轨改动；本场景专项侧重已通过（重构或等价改写以行为等价验证、无逻辑被静默增删）。
- 验证使用了可说明的基线、条件和覆盖范围。
- graph 中所有必需节点都已完成、否决、回滚或明确阻塞，没有悬空分支。
- 无关键工作仍停留在“已实现但未验证”状态。
- 旁路问题已分类，不会被误认为当前目标的一部分。
- 最终结论明确为保留、回滚、否决或进入下一目标。
